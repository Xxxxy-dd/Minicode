# MiniCode Agent 18 天实现计划

## 总体目标

在 18 天内完成 MiniCode Agent 第一版可展示项目。第一版不追求功能大而全，而是要做到：

- 能真实运行本地 Coding Agent CLI。
- 有清晰的 Tool Runtime、权限系统、Trace、Query Loop。
- 实现简历中的核心亮点：Skill 路由、自进化记忆、上下文压缩、多 Agent 协作、安全审查、Harness 评测。
- 每天都有可运行交付物，避免只写架构不落地。

## 开发节奏

```text
第 1-6 天：Agent 基础设施
第 7-12 天：核心亮点模块
第 13-16 天：Harness、Benchmark 和量化实验
第 17-18 天：项目打磨、README、简历和面试材料
```

每天结束必须满足三个条件：

- `pytest` 通过。
- CLI 至少有一个当天相关的可运行命令。
- README 或 docs 记录当天新增能力和使用方式。

推荐默认运行环境：

```powershell
E:\conda\envs\minicode\python.exe -m pytest tests
E:\conda\envs\minicode\Scripts\minicode.exe --help
```

## Day 1：只读 Tool Runtime

实现内容：

- `ToolRegistry`
- `list_files`
- `read_file`
- `search_code`
- `git_status`
- `git_diff`

设计重点：

- 所有工具通过统一注册表查找和执行。
- 工具返回结构化 `ToolObservation`。
- 只读工具不修改工作区。

交付物：

- `minicode tools list`
- `minicode tools run list_files`
- `minicode tools run read_file --path README.md`

验收标准：

- 可以列出工具。
- 可以读取 workspace 内文件。
- 读取不存在文件时返回清晰错误。
- 单元测试覆盖正常路径和错误路径。

## Day 2：权限系统 v1

状态：已完成。

实现内容：

- `RiskLevel`
- `PermissionPolicy`
- `PathSandbox`
- `allow / ask / deny`

设计重点：

- 所有工具执行前都经过权限判断。
- workspace 外路径默认阻断。
- 只读工具默认 `allow`。
- 高风险工具默认 `ask` 或 `deny`。

交付物：

- `PermissionDecision`
- path sandbox 测试。
- tool execution 前置权限检查。

验收标准：

- 读取 workspace 内文件允许。
- 读取 workspace 外文件阻断。
- blocked 工具无法执行。

## Day 3：写入工具 v1

实现内容：

- `edit_file`
- `write_file` 限制版。
- patch 风格编辑接口。

设计重点：

- 只允许修改 workspace 内文件。
- 写入前记录原始文件摘要。
- 写入后可通过 `git_diff` 审计。
- 写操作默认需要 approval 策略。

交付物：

- `minicode tools run edit_file ...`
- 文件修改 trace。
- 写入工具测试。

验收标准：

- 可以安全修改临时测试文件。
- 无法写 workspace 外路径。
- 修改后能通过 git diff 看到变化。

## Day 4：Shell 和 Test 工具

实现内容：

- `run_shell`
- `run_tests`
- timeout 控制。
- stdout / stderr / exit code 捕获。
- 危险命令拦截。

设计重点：

- shell 工具是高风险入口，必须接权限系统。
- 命令执行必须有 timeout。
- 输出过长时标记 `truncated`。

交付物：

- `minicode tools run run_tests --command "pytest tests"`
- shell command observation。

验收标准：

- 可以运行安全命令。
- 可以运行测试命令并捕获退出码。
- 危险删除命令被阻断。

## Day 5：Trace Store

实现内容：

- SQLite trace db。
- `TraceEvent`。
- `run_started`
- `tool_requested`
- `permission_checked`
- `tool_finished`
- `run_finished`

设计重点：

- 每次工具调用都能回放。
- trace 记录输入、输出、错误、耗时和风险等级。
- trace 文件保存在 `.minicode/traces/` 或 SQLite 中。

交付物：

- `minicode trace <run_id>`
- trace persistence 测试。

验收标准：

- 执行工具后能查到 trace。
- 失败工具也会记录 trace。
- trace 不记录敏感环境变量。

## Day 6：Agent Loop v1

实现内容：

- 状态机骨架：
  - `INIT`
  - `LOAD_CONTEXT`
  - `PLAN`
  - `ACT`
  - `OBSERVE`
  - `VERIFY`
  - `DONE / FAILED`

设计重点：

- 先做非 LLM 或半模拟版本。
- 重点是跑通状态流转和 trace。
- 每个 phase 都记录 trace event。

交付物：

- `minicode run "inspect project"`
- 生成完整 run trace。

验收标准：

- run 能从 `INIT` 走到 `DONE`。
- run 失败时有明确失败原因。
- 状态流转有测试覆盖。

## Day 7：模型适配层

实现内容：

- `ModelClient` interface。
- OpenAI compatible adapter 或 LiteLLM adapter。
- prompt builder。
- structured response parser。

设计重点：

- 模型调用和 Agent Core 解耦。
- 支持后续替换模型。
- API key 从环境变量或配置读取。

交付物：

- `minicode run` 可调用真实模型。
- mock model 测试。

验收标准：

- 没有 API key 时给出清晰错误。
- mock model 可用于单元测试。
- prompt 构造稳定可测试。

## Day 8：Query Loop v2

实现内容：

- 模型决策下一步。
- 工具调用。
- observation 注入下一轮。
- retry limit。
- stop policy。

设计重点：

- 模型不直接执行动作，只能请求工具。
- 每轮必须有最大步数限制。
- 工具失败后进入 replan 或 failed。

交付物：

- 能完成“读取文件并总结项目”类任务。
- Agent run trace 包含 model request 和 tool call。

验收标准：

- Agent 能连续调用多个只读工具。
- 超过最大步数会停止。
- 工具失败不会导致无限循环。

## Day 9：Skill System v1

实现内容：

- `SkillRegistry`
- `metadata.yaml`
- `SKILL.md` loader。
- 内置 skills：
  - `debugging`
  - `test-writing`
  - `code-review`

设计重点：

- Skill 是能力包，不只是 prompt 字符串。
- Skill 有名称、描述、标签、适用场景和示例。

交付物：

- `minicode skills list`
- `minicode skills show debugging`

验收标准：

- 能加载内置 skill。
- 缺失或格式错误的 skill 有清晰错误。
- Skill 内容能注入 prompt builder。

## Day 10：Skill 路由

实现内容：

- 任务意图识别。
- metadata filter。
- 关键词召回。
- LLM rerank 可选。
- top-k skill injection。

设计重点：

- 先实现确定性关键词召回。
- LLM rerank 作为增强，不阻塞基础功能。
- 记录每次选择 Skill 的原因。

交付物：

- debug/test/review 任务自动选择不同 Skill。
- trace 中记录 skill selection。

验收标准：

- “修复测试失败”选择 debugging 或 test-writing。
- “审查 diff”选择 code-review。
- 没有合适 skill 时不强行注入。

## Day 11：Memory System v1

实现内容：

- `MemoryRecord`
- `project_memory`
- `user_memory`
- `procedure_memory`
- `failure_memory`
- memory read/write。
- reflection candidates。

设计重点：

- Memory 必须有来源、时间、置信度和类型。
- 不存储密钥。
- 不确定内容低置信度保存或跳过。

交付物：

- `minicode memory list`
- `minicode memory add`
- run 结束后生成 memory candidate。

验收标准：

- 可以写入和读取 memory。
- 重复 memory 能被识别。
- memory 加载进入 context。

## Day 12：Context Compression v1

实现内容：

- `TaskStateCompressor`
- 工具输出截断和摘要。
- history summary。
- hot / warm / cold context。

设计重点：

- 压缩不是普通摘要，而是结构化 `TaskState`。
- 必须保留目标、约束、失败尝试、已修改文件和下一步动作。

交付物：

- trace 中出现 `context_compressed` event。
- compression ratio 指标。

验收标准：

- 长工具输出会触发压缩。
- 压缩结果包含关键字段。
- 压缩失败时有 fallback。

## Day 13：Subagent v1

实现内容：

- `spawn_subagent` tool。
- Explorer Agent。
- Reviewer Agent。
- 最大轮数。
- 限定工具集合。
- 结构化返回。

设计重点：

- 子 Agent 是受控工具，不是自由自治 peer。
- Main Agent 保留最终决策权。
- 子 Agent 默认只读，Reviewer 只审查 diff。

交付物：

- `minicode run "review current diff"` 可触发 Reviewer。

验收标准：

- 子 Agent 返回结构化结果。
- 子 Agent 超过最大轮数会停止。
- 子 Agent 不能绕过权限系统。

## Day 14：Harness v1

实现内容：

- `task.yaml`
- sample repo reset。
- success command。
- metrics collection。

设计重点：

- 先支持本地小样例。
- 每个任务有 prompt、初始仓库、成功条件。
- eval run 和普通 run 共用 trace。

交付物：

- `minicode eval examples/tasks`
- 单任务评测报告。

验收标准：

- 可以运行一个 benchmark task。
- 可以判断 pass / fail。
- 可以记录 tool_calls、runtime、files_changed。

## Day 15：Benchmark Tasks

实现 10 个小任务：

- 修复 pytest 失败。
- 添加一个小功能。
- 修复边界条件。
- 重构重复代码。
- 更新文档。
- 修复类型错误。
- 修复路径处理错误。
- 增加缺失测试。
- 简单代码审查。
- 危险命令拦截测试。

设计重点：

- 任务不要过大。
- 每个任务都能用命令验证。
- 保留失败案例，方便展示 Agent 局限。

交付物：

- `examples/tasks/`
- `examples/repos/`
- benchmark README。

验收标准：

- 至少 10 个任务可被 Harness 读取。
- 至少 5 个任务有自动成功判定。
- eval report 能展示通过率。

## Day 16：消融实验

实现配置：

- `baseline`：无 memory、无 skill、无 compression、无 subagents。
- `skill_only`：开启 skill routing。
- `memory_skill`：开启 memory 和 skill。
- `full`：开启 skill、memory、compression、reviewer subagent。

设计重点：

- 对比结果要能写进简历。
- 即使样本少，也要清楚展示实验方法。

交付物：

- `minicode eval --config baseline`
- `minicode eval --config full`
- Markdown evaluation report。

验收标准：

- 报告包含 pass rate、tool calls、runtime。
- 报告说明不同配置差异。
- 结果可复现。

## 推荐执行顺序

不要一开始就接 LLM。推荐顺序：

```text
工具层
-> 权限层
-> Trace
-> 状态机
-> 模型接入
-> Skill
-> Memory
-> Compression
-> Subagent
-> Harness
```

这样每天都能在前一天的基础上前进，不会变成 prompt 堆叠。
