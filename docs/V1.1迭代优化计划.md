# MiniCode Agent V1.1 八天迭代优化计划

## 目标

V1.1 的目标不是重写 MiniCode Agent，而是在 V1 已经可运行、可扩展、可评测的基础上，优先补齐真实使用时最影响体验、稳定性和后续扩展的短板。

本轮按 8 天推进，每天都要产出可验证能力：

- 保留 V1 的基础命令和运行路径：`run`、`chat`、`skills`、`memory`、`eval`。
- 优先收敛会阻碍扩展的硬编码：skill 选择、工具意图、planner fallback、direct chat、subagent 行动计划。
- 原本计划中的内置 skills、工具增强、CLI、memory、benchmark、安全和发布材料仍然保留。
- 不太紧要、偏治理类的优化统一放到 Day 8 收尾，避免前期分散主线。

## 优先级

### P0：必须优先处理

- 统一 skill 选择路径，清理或替换 `RuleBasedPlanner.select_skill()` 的静态关键词表。
- 把工具意图保护从 `AgentLoop` 中抽出，形成可复用 intent rules/policy。
- 合并 direct answer、工具意图解析、CLI direct chat 的分散关键词规则。
- 改造无模型 planner fallback，减少对具体工具名和 `README.md` 的固定依赖。
- 确保新增工具、skill、subagent 能通过声明和配置扩展，而不是继续改主流程分支。

### P1：本轮尽量完成

- 新增内置 skills：`refactoring`、`release-polish`、`security-review`、`repo-onboarding`。
- 增强工具系统：`apply_patch` 风格编辑、formatter、linter、repo inspection。
- 增强 memory 可解释性、冲突/stale 处理和召回原因 trace。
- 增强 context compression，保留结构化证据引用。
- 增强 subagent role strategy 和 reviewer 输出结构。
- 扩展 benchmark/eval，使 V1.1 的能力和回归风险可衡量。

### P2：Day 8 集中收尾

- skill metadata parser/schema、registry manifest、报告 renderer 等治理项。
- README 假设、固定英文模板、测试入口样例等低风险硬编码。
- trace schema version、配置贯通、metrics/state 小幅清理。

## 每日通用验收

每天结束需要满足：

- 相关单元测试通过，或清楚记录未运行原因。
- 至少有一个 CLI 命令可以演示当天新增能力。
- README 或 docs 记录新增能力、使用方式或剩余限制。
- trace 中能看到关键行为的 reason、decision 或 fallback 信息。
- 不破坏 V1 基础命令：`run`、`chat`、`skills`、`memory`、`eval`。

## Day 1：Skill 路由与内置 Skill 扩展

### 实现内容

- 新增或完善内置 skills：
  - `refactoring`：行为保持型重构。
  - `release-polish`：发布前检查、README、示例、smoke test。
  - `security-review`：路径、命令、密钥、依赖风险审查。
  - `repo-onboarding`：快速理解陌生项目结构。
- 统一 skill 选择入口：
  - 主流程只依赖 `SkillRouter`。
  - 清理 `RuleBasedPlanner.select_skill()`，或改成委托 `SkillRouter`。
  - 避免 rule planner 和 skill router 两套规则分叉。
- 改进 skill route 可解释性：
  - trace/CLI 展示 top candidates、score、selected reason、rerank fallback reason。
  - 增加未命中原因或低分候选摘要，便于调试。
- 调整测试，不再把内置 skill 集合锁死为三个固定项。

### 设计重点

- skill 内容应该是工作流，而不是泛泛提示词。
- `metadata.yaml` 中的 aliases、tags、applies_to、examples 要能驱动路由，不把同义词继续散落在 router 代码里。
- LLM rerank 仍然是可选增强，确定性路由必须单独可用。

### 验收标准

- `minicode skills list --workspace .` 能看到新增 skill。
- `minicode skills route "refactor duplicate code" --workspace .` 命中 `refactoring`。
- `minicode skills route "prepare V1.1 release" --workspace .` 命中 `release-polish`。
- `minicode skills route "审查 diff 风险" --workspace .` 命中 `code-review` 或 `security-review`，并能解释原因。
- 新增 skill 有 registry、metadata、route 测试。

## Day 2：Intent 规则、Planner Fallback 与 Direct Answer 收敛

### 实现内容

- 抽出统一 intent rules：
  - 覆盖 append、overwrite、create、delete、edit、read、search、run tests、direct answer。
  - 由 `ToolSpec.intents` 和共享规则表共同驱动。
  - `AgentLoop` 不再直接维护自然语言 token 列表。
- 合并这些分散规则：
  - `AgentLoop.INTENT_GUARD_RULES`。
  - `models/parser.py::is_tool_intent_action()`。
  - `cli/live_ui.py::is_direct_chat_query()` 和 `direct_chat_reply()`。
  - planning prompt 中 direct-answer policy 的固定示例。
- 补充 route debug 信息：
  - 对完全无候选的输入记录 `no_match_reason` 或 `debug_summary`。
  - `skills route` 增加可选 `--llm-rerank`，让 CLI 能直接演示 rerank/fallback 原因。
- 改造 rule-based fallback planner：
  - 基于工具能力、风险等级、只读优先和 workspace 结构选择行动。
  - 减少 `read_file README.md`、`list_files`、`spawn_subagent` 的固定分支。
  - 保留无模型 fallback 的简单性。
- 动态生成能力描述：
  - direct chat 的“有哪些工具/能做什么”从 registry 摘要生成。

### 设计重点

- intent rules 应小而明确，可以先是代码内规则表，但要独立于 `AgentLoop`。
- 每个拦截都必须有可读 reason，并写入 trace。
- 不引入复杂 classifier，先用共享规则表解决重复维护。

### 验收标准

- append/overwrite/create/delete/edit 的中英文意图测试通过。
- 模型返回缺失 action 但 next_actions 含工具意图时仍能被正确拒绝。
- `minicode chat --no-model --preview "你有什么工具"` 能输出基于 registry 的能力摘要。
- 无 `README.md` 的 workspace 仍可完成安全 fallback 首步。

## Day 3：工具系统增强与声明化运行时

### 实现内容

- 新增或改进工具：
  - `apply_patch` 风格编辑工具，适合小范围改动。
  - `run_formatter`，封装显式 formatter 命令。
  - `run_linter`，封装显式静态检查命令。
  - `inspect_repo`，结构化返回目录、语言、测试命令候选、入口文件候选。
- 强化 `ToolSpec`：
  - 补齐 `duplicate_policy`、`state_effects`、`intents`、`capture_full_output`、`counts_as_subagent_call`、`subagent_roles`。
  - 增加或预留 capability/path_arg/command_arg 这类声明，供 planner、permission、context 使用。
- 收敛 CLI 参数映射：
  - `tools run` 的 help、默认值、枚举说明尽量从 `ToolSpec.input_schema` 生成。
  - 手工参数保留兼容，但新增工具不再必须改多处 CLI 分支。
- 扩展 `ToolIntent` 和 intent guard：
  - 增加 read/search/run-test/shell 等非写入类 intent，让 planner、parser、CLI 和权限提示能共享更完整的工具意图。
  - guard 判断不只看目标文本和工具 intent，还要结合 action arguments，例如 path、command、overwrite、append_strategy。
- 改进 planner fallback：
  - `choose_entry_context_file()` 支持接收 goal/task，按“读文档、查配置、跑测试、看入口”等不同目标选择入口文件。
  - 对多入口 workspace 输出选择原因，避免再次把 `README.md` 或固定文件顺序写死。
- 工具运行体验继续收口：
  - `inspect_repo` 改成两阶段扫描：优先检查根目录 marker 和入口文件，再做文件样本统计，避免大仓库中被目录排序和 `max_files` 截断影响判断。
  - `run_formatter`、`run_linter` 与普通 `run_shell` 在 trace/eval/report 中区分 `quality_tool`、`command_kind` 和 exit-code policy。
- 拆分 append 格式策略：
  - json/csv/toml/yaml/code/text 追加逻辑沉到策略表。
  - 新增格式只注册策略，不改主流程。

### 设计重点

- 工具仍然必须经过 `ToolExecutor`、`PermissionPolicy` 和 trace。
- 写入类工具默认仍然需要 approval。
- formatter/linter 先支持显式命令，不做过度猜测。
- 横切行为优先声明在 `ToolSpec`，运行层按声明统一处理。

### 验收标准

- `minicode tools list` 能看到新增工具。
- `minicode tools run inspect_repo --workspace .` 返回结构化摘要。
- 新增工具失败时返回结构化 `ToolObservation`。
- 写入或命令类工具仍然受权限系统控制。
- 工具有单元测试和至少一个 CLI 示例。

## Day 4：安全 Policy、Trace Redaction 与上下文压缩

### 实现内容

- 安全策略增强：
  - 增加 dirty worktree 提示。
  - 写文件前必须生成可视化 diff preview，并要求用户明确同意后才执行写入；trace 中保存 diff 摘要、用户决策、变更文件和审批原因。
  - `apply_patch`、`write_file`、`append_file`、`create_file`、`edit_file`、`delete_file` 都纳入同一套 preview -> approval -> execute 流程。
  - preview 必须在真实写入前生成，用户拒绝时文件保持不变；禁止通过“先写入再展示 git diff”的方式实现审批。
  - 区分 preview 权限和 execute 权限：preview 可以读取/模拟变更，真正写入仍必须走写入审批。
  - 按工具类型生成 diff：`apply_patch` 展示 patch hunks/stat；`edit_file` 展示 exact replacement before/after；`write_file`、`append_file` 先模拟新内容再 diff；`create_file` 展示新增文件摘要；`delete_file` 展示删除文件摘要。
  - 扩展危险命令规则，覆盖 Windows 和跨平台命令。
  - 检查 `.env`、密钥、SSH 文件等敏感路径保护。
  - 将敏感路径、工作区越界、危险命令、重复执行、意图 mismatch 纳入统一 policy/guard 体系。
- 权限策略声明化：
  - `PathSandbox.path_argument_names` 不再只靠静态元组，优先从工具 schema/spec 标注读取 path 参数。
  - shell command safety 规则集中配置，并保证每条 deny 都有 reason。
- trace redaction：
  - 在 TraceStore 或统一 trace helper 层做 payload sanitizer。
  - 覆盖 arguments、metadata、memory、prompt 摘要中的 secret-like 字段。
  - 覆盖 diff preview 和拒绝/审批事件，避免把 `.env`、token、密钥或敏感文件片段写入 trace。
- context compression 增强：
  - 抽出 `ContextPolicy`，管理压缩阈值、最近 observation 数量、总字符上限。
  - `TaskStateCompressor` 从当前运行 registry 注入 tool effects，而不是创建默认 registry。
  - 增加按工具类型的事实抽取，保留 observation id、turn、path 等 evidence refs。

### 设计重点

- AgentLoop 只编排流程，不承载具体工具知识。
- 安全策略集中在 permission/tool executor/guard 层。
- 不做不可解释的“智能拦截”，每次 deny 都要有 reason 和测试。
- 写入审批不能只展示工具名；必须展示用户可读的 diff/stat，并记录用户是否同意。
- 大 diff 默认只展示 changed files、insertions/deletions 和每个文件前若干 hunks；完整 diff 通过 trace 或 `/diff --full` 这类入口查看。
- context 压缩先保持确定性，不引入复杂向量系统。

### 验收标准

- 危险命令测试覆盖新增规则。
- 敏感路径写入或读取符合预期策略。
- 权限相关 trace 清晰记录 allow/ask/deny 和 reason。
- 写入类工具在执行前能展示 diff preview；用户拒绝时不修改文件，用户同意后才执行。
- `apply_patch` 至少展示 changed files、diff stat 和关键 hunks；普通写入工具至少展示 before/after diff 或 create/delete 摘要。
- 拒绝写入也必须有 trace 事件，包含工具名、文件摘要、拒绝结果和审批原因，便于解释“为什么没有改文件”。
- diff preview 覆盖 CRLF/LF、UTF-8 BOM、中文文件名、路径带空格和 `patch-file` 场景。
- 长输出 observation 触发压缩后，`TaskState` 保留文件、失败、事实和 evidence refs。
- 自定义/禁用工具场景下 context tool effects 不再来自固定默认 registry。

## Day 5：Memory 可解释性、冲突处理与反思质量

### 实现内容

- 承接 Day 4 安全边界：
  - Memory 写入、召回、reflection 候选和 CLI 展示复用统一 redaction/secret policy，不再单独维护脱敏规则。
  - Memory trace payload 必须只保存脱敏后的 content、reason、metadata 摘要。
  - 将 Day 4 的 `evidence_refs` 思路延伸到 memory recall/admission，保留触发召回的 query、record id、kind、score/原因和来源 run id。
- 增强 memory list/search：
  - 显示来源 run id、kind、confidence、admission reason、tags、metadata 摘要。
  - 增加“为什么召回这条记忆”的 trace 字段。
  - 召回支持按 kind、tags、stale/conflict 状态过滤。
- 增加 memory 冲突和 stale：
  - 同 workspace 下相似但内容相反的 memory 给出提示。
  - 支持手动标记 stale 或降权。
  - 新记忆能覆盖或降低旧的低置信度记忆影响。
- 改进 reflection：
  - deterministic reflection 不再无条件记录过泛化模板。
  - 把候选生成、admission threshold、过滤原因集中到 memory policy。
  - LLM memory fallback、filtered_count、admission_reason 暴露给 trace/CLI。
- 扩展 secret 检测：
  - memory content、reason、tags、metadata 都走统一 secret policy。
  - 添加包含 API key、token、private key、`.env` 内容片段的拒绝/脱敏测试。

### 设计重点

- 不让 LLM 直接决定最终写入，仍然复用确定性 admission rules。
- 冲突检测先做简单规则，不引入向量数据库。
- Memory 变化必须能追到 run id、admission reason 和 recall reason。
- Memory 的安全策略与 trace redaction 保持同源，避免 Day 4 和 Day 5 出现两套 secret 判断。

### 验收标准

- `minicode memory list --query pytest` 显示更完整元信息。
- `minicode memory list --kind failure_memory` 可过滤类型。
- 新增 stale、conflict、recall reason 行为有测试。
- Agent run 的 trace 中能看到 memory recall 和 memory admission/rejection 原因。
- Memory 相关 trace 和 CLI 输出不泄露 token、API key、private key 或 `.env` 内容。
- Memory recall/admission 事件包含 record id、source run id、kind、confidence、reason 和 evidence refs。

## Day 6：Agent Team 基础协议、Reviewer Evidence 与 Eval 判定增强

### 实现内容

- Agent Team 基础协议：
  - 在现有 subagent runner 之上定义轻量 `TeamRun` / `AgentTeam` / `RoleProfile` 概念，先作为中心 orchestrator 的结构化协议，不做真正并行执行。
  - 支持声明 team id、parent run id、roles、allowed tools、allowed intents、max steps、max risk、path scope 和 evidence contract。
  - 先启用 explorer/reviewer 两类 role；implementer role 只保留接口和文档，不在 V1.1 赋予独立写权限。
  - trace 记录 `team_started`、`team_role_completed`、`team_finished`，包含 role、任务、工具摘要、evidence refs 和失败原因。
- Worktree/Fork 隔离方向预留：
  - 新增 workspace isolation plan：检测当前仓库是否支持 git、当前 branch、dirty state、可选 worktree path/name 和不能创建的原因。
  - V1.1 不自动创建 fork/worktree、不自动 merge；只在 trace/docs 中形成 `team_workspace_plan`，为 V1.2 的隔离执行铺路。
  - dirty worktree 时 reviewer/team 输出必须标注 merge risk，不直接覆盖或合并用户未提交变更。
- Reviewer evidence contract：
  - 将 reviewer/explorer 的固定工具序列拆成 role profile + evidence collectors。
  - reviewer 输出结构化字段：`changed_files`、`risks`、`test_suggestions`、`evidence`、`merge_blockers`。
  - reviewer 风险识别不只看 `TODO`、`pass`、changed files，增加 diff、测试、敏感文件、删除/覆盖、未验证写入等基础 detector。
  - findings 保留结构化 evidence，而不是只压成 500 字文本。
- Benchmark 任务扩展：
  - 重构任务：要求行为不变且测试通过。
  - 安全任务：验证危险命令被拒绝。
  - 外接 skill 任务：验证 workspace skill 能影响路由。
  - CLI 文档任务：验证 release polish 能力。
  - 长上下文任务：压测 compression。
  - Agent Team/reviewer 任务：验证中心调度、role evidence、merge blocker 和结构化风险输出。
- Eval 判定增强：
  - 支持 trace assertions、file diff assertions、forbidden tool assertions。
  - `analysis_only` 不只看 agent phase，可以检查 expected observation。
  - 支持 team assertions：role 是否运行、是否产出 evidence、是否记录 merge blocker。
  - success command 的风险、cwd、timeout 写入报告。

### 设计重点

- Agent Team 是中心化 orchestrator + bounded role workers，不改成完全自治 peer agents。
- Fork/Worktree 在 V1.1 只做能力探测、计划和 trace，不做真正隔离分支执行与自动 merge。
- Subagent/role worker 默认仍然受控、只读、bounded；写入能力仍由主 Agent 的工具权限和审批边界管理。
- benchmark 每个任务要有 expected outcome、category、tags、difficulty。
- 能自动判断的任务优先加 success command 或 trace assertion。

### 验收标准

- `minicode eval examples/tasks --config baseline` 可运行。
- `minicode eval examples/tasks --config all` 继续生成 Markdown、JSON、CSV 报告。
- V1.1 新任务至少 6 个，覆盖 skill、memory、context、security、subagent、CLI。
- trace 中能看到 team lifecycle：`team_started`、`team_role_completed`、`team_finished` 或等价事件。
- reviewer role 输出 `changed_files`、`risks`、`test_suggestions`、`evidence` 和 `merge_blockers`。
- workspace isolation plan 能报告 git/worktree 可用性、dirty state 和不执行自动 worktree/merge 的原因。

## Day 7：CLI 交互、可观测性与发布材料

### 实现内容

- 增强 `minicode chat`：
  - 显示当前 phase：load_context、select_skill、plan、act、verify、reflect。
  - 显示最近 tool call 摘要。
  - 增加 `/status` 的实际反馈。
  - 增加 `/memory`、`/skills`、`/trace` 的轻量查看入口。
  - 增加 `/diff` 或等价入口，展示最近一次待审批/已执行写入的可视化 diff。
- 写入审批 UI：
  - 在 approval 提示前展示 diff/stat，用户确认后才执行写入。
  - 用户拒绝时在对话中明确显示“未应用变更”，并把拒绝事件写入 trace。
  - 支持普通终端文本 diff；后续可扩展 side-by-side，但 V1.1 先保证可读、可审、可拒绝。
- 统一 CLI renderer：
  - phase 摘要、tool call 摘要、memory 摘要、skill route 摘要复用 formatter/renderer。
  - `/status`、`/memory`、`/skills`、`/trace` 使用同一套短摘要组件。
  - diff preview、`/diff` 和 trace diff 摘要复用同一套 `DiffPreview`/`DiffRenderer`，避免 CLI、chat、trace 三套展示分叉。
  - 将 `memory list` 的文本摘要抽成 `MemoryRenderer`，让 `memory list`、后续 `/memory`、trace memory 摘要复用同一套格式。
  - 增加 CLI smoke matrix，覆盖 `memory add -> list -> stale -> list --status stale`、write preview、patch-file 和权限拒绝等关键链路。
- 发布材料：
  - 更新 README 的 V1.1 能力说明。
  - 更新 demo 命令。
  - 增加 V1.1 release checklist。
  - 整理 V1 -> V1.1 的变化摘要和剩余限制。

### 设计重点

- 不把 CLI 做成复杂 TUI，保持当前布局稳定。
- 新增反馈以可读为主，不追求动画。
- approval 交互仍用 `y/N`，但提问前必须展示 diff/stat；细节进入 trace 和安全摘要。
- 命令输出要短，避免挤压主对话区。

### 验收标准

- `/help`、`/status`、`/clear`、`/exit`、`/memory`、`/skills`、`/trace` 都有明确反馈。
- `/diff` 能展示最近一次写入 preview 或最近一次实际 diff 摘要。
- 写入类工具在 chat UI 中会先展示 diff 并等待用户同意；拒绝时文件保持不变。
- 完成一次 run 后，聊天界面能看到最近 tool call、phase、selected skill 和 trace id。
- `minicode chat --workspace . --no-model --preview` 可运行。
- README、docs、demo 说明 V1.1 新能力、使用方式和剩余限制。

## Day 8：低优先级治理、回归矩阵与发布打磨

### 实现内容

- Skill 治理：
  - 将 `parse_simple_yaml()` 替换为标准 YAML parser，或明确保留简化 parser 并加 schema version/错误提示。
  - 为 skill metadata 增加 schema 校验和迁移说明。
- 配置和 runtime 贯通：
  - 让 `MiniCodeConfig.trace_db_path`、`max_subagent_steps`、`require_approval_for_writes` 真正影响 runtime/policy，或删除无效配置。
  - `RuntimeContext.create()` 支持从 config 传入 trace/memory paths。
- Trace 和 state 治理：
  - TraceEvent 增加 schema version 或事件约定文档。
  - 统一 state 更新入口，补齐 `tool_history`、`approval_events` 等字段的实际使用。
  - eval 报告 renderer 从 metrics schema 生成，减少手工拼接遗漏。
- Memory 治理：
  - 将 memory admission、secret 判断、conflict 检测、recall score/reason 从 `MemoryStore` 抽到 `memory/policy.py`，让 Store 只负责持久化和查询。
  - 为 JSONL fallback、SQLite migration、stale/conflict 状态增加小型回归矩阵。
- 测试样例补强：
  - 无 README workspace。
  - 多入口文件。
  - 中文文件名。
  - 非 Python 项目。
  - 读写同一文件多步操作。
  - 先读后改。
  - 重复失败重试。
- 文档和展示收尾：
  - 统一处理 README/docs 的末尾空行和无关格式 churn。
  - 为内置 skill 的 `SKILL.md` 增加简短中文摘要，改善 `skills show` 的中文阅读体验。
- Intent/CLI 治理收尾：
  - 将当前 `intent.py` 中的工具意图、direct chat 判断、回复模板进一步拆成 `tool_intents`、`direct_chat`、`capability_summary` 等小模块。
  - 将 direct chat 的能力摘要 renderer 与 CLI 其他 renderer 统一，避免输出样式和术语继续分散。
  - 将中英文短语表迁移到可校验配置或集中 manifest，并补充 shared intent module 的专门测试矩阵。
- CLI/schema 治理收尾：
  - 基于 `ToolSpec.input_schema` 生成或校验 `tools run` 的参数说明，减少新增工具时手动同步 CLI 参数。
  - 为新工具补 CLI 级 smoke matrix，并把 `patch-file`、显式 argv、权限拒绝、危险命令拦截纳入发布前回归。
- 全量回归和发布检查：
  - 跑全量测试和关键 eval。
  - 修正文档中的旧路径、旧命令、旧能力描述。

### 设计重点

- Day 8 不承担大功能，只做收口、治理、回归和发布质量。
- 不为低优先级治理引入大规模架构重写。
- 若时间不足，优先保留测试和文档，推迟内部整理。

### 验收标准

- `python -m pytest -q` 通过。
- `minicode eval examples/tasks --config baseline` 可运行。
- `minicode eval examples/tasks --config all` 生成报告。
- V1.1 release checklist 完成。
- docs 中说明已完成能力、已知限制、推迟到 V1.2/V2 的事项。
