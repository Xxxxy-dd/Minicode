# MiniCode Agent V1.1 迭代优化计划

## 目标

V1.1 的目标不是重写 MiniCode Agent，而是在 V1 已经可运行、可扩展、可评测的基础上，补齐真实使用时最影响体验和能力的短板。

本轮控制在一周以内，优先做能直接提升 agent 可用性的改进：

- 增强内置 skills，让 agent 更会处理常见开发任务。
- 增强工具系统，让修改、验证、审查更稳定。
- 改善 CLI 反馈，让用户更清楚 agent 正在做什么。
- 提升 memory 可解释性，减少错误记忆的长期影响。
- 扩展 benchmark，能衡量 V1.1 是否真的变强。

## 迭代节奏

```text
Day 1: 内置 Skill 扩展
Day 2: 工具系统增强
Day 3: CLI 交互与可观测性
Day 4: Memory 可解释性与冲突处理
Day 5: Benchmark 任务扩展
Day 6: 安全与回归检查
Day 7: V1.1 打磨与发布材料
```

每天结束需要满足：

- 相关测试通过。
- 至少有一个 CLI 命令可以演示当天新增能力。
- README 或 docs 记录新增能力和使用方式。
- 不能破坏 V1 的基础命令：`run`、`chat`、`skills`、`memory`、`eval`。

## Day 1：内置 Skill 扩展

### 实现内容

新增或完善内置 skills：

- `refactoring`：行为保持型重构。
- `release-polish`：发布前检查、README、示例、smoke test。
- `security-review`：路径、命令、密钥、依赖风险审查。
- `repo-onboarding`：快速理解陌生项目结构。

### 设计重点

- 每个 skill 必须有清晰的 `metadata.yaml` 和 `SKILL.md`。
- skill 内容应该是工作流，而不是泛泛提示词。
- 避免过多 skill 同时命中，必要时调整 aliases 和 route 权重。

### 验收标准

- `minicode skills list --workspace .` 能看到新增 skill。
- `minicode skills route "refactor duplicate code" --workspace .` 能命中 `refactoring`。
- `minicode skills route "prepare V1.1 release" --workspace .` 能命中 `release-polish`。
- 新增 skill 有路由测试。

## Day 2：工具系统增强

### 实现内容

优先新增或改进：

- `apply_patch` 风格编辑工具：比整文件写入更适合小改动。
- `run_formatter`：封装常见 formatter。
- `run_linter`：封装静态检查。
- `inspect_repo`：结构化返回项目目录、语言、测试命令候选。

### 设计重点

- 工具仍然必须经过 `ToolExecutor`、`PermissionPolicy` 和 trace。
- 写入类工具默认仍然需要 approval。
- formatter/linter 不应该猜测过度，先支持显式命令，再逐步自动识别。
- 横切行为优先声明在 `ToolSpec`，不要在 `AgentLoop`、CLI 或 subagent runner 里按工具名逐个写判断。
- 已抽象的声明包括：重复成功动作拦截、状态影响、完整输出保留、subagent 调用计数、subagent 角色、文件操作意图。
- 后续新增工具时先补齐 `duplicate_policy`、`state_effects`、`intents`、`capture_full_output`、`counts_as_subagent_call`、`subagent_roles` 等声明，再让运行层按声明统一处理。
- 继续收敛工具参数 schema：把常用参数、枚举值、默认值和 CLI help 统一从工具声明生成，避免 prompt、CLI、测试里各维护一份。
- 继续收敛格式感知写入策略：把 `append_file` 的 text/markdown/code/json/csv/toml/yaml 追加规则沉到独立格式策略表，后续新增 XML、INI、requirements 等格式时不改主流程。

### 验收标准

- `minicode tools list` 能看到新增工具。
- 工具失败时返回结构化 `ToolObservation`。
- 写入或命令类工具仍然受权限系统控制。
- 工具有单元测试和至少一个 CLI 示例。

## Day 3：CLI 交互与可观测性

### 实现内容

增强 `minicode chat`：

- 显示当前 phase：如 load_context、select_skill、plan、act、verify。
- 显示最近 tool call 摘要。
- 增加 `/status` 的实际反馈。
- 增加 `/memory`、`/skills`、`/trace` 的轻量查看入口。

### 设计重点

- 不把 CLI 做成复杂 TUI，保持当前布局稳定。
- 新增反馈以“可读”为主，不追求动画。
- 命令输出要短，避免挤压主对话区。
- approval 交互只问 `y/N`，不在输入提示里展示工具名、路径或内容；细节进入 trace 和安全摘要。
- 后续把命令摘要、phase 摘要、tool call 摘要统一成 formatter/renderer 注册表，不在 UI 层按事件类型和工具名散写。
- `/status`、`/memory`、`/skills`、`/trace` 应复用同一套短摘要组件，避免每个命令各自拼字符串。

### 验收标准

- `/help`、`/status`、`/clear`、`/exit` 都有明确反馈。
- 完成一次 run 后，聊天界面能看到最近 tool call 和 phase 结果。
- CLI preview 测试通过。

## Day 4：Memory 可解释性与冲突处理

### 实现内容

增强 memory：

- `memory list` 显示来源 run id、kind、confidence、admission reason。
- 增加“为什么召回这条记忆”的 trace 字段。
- 增加简单冲突检测：同 workspace 下相似但内容相反的 memory 给出提示。
- 增加 memory 降权或手动标记 stale 的入口。

### 设计重点

- 不让 LLM 直接决定最终写入，仍然复用确定性 admission rules。
- 冲突检测先做简单规则，不引入复杂向量系统。
- 所有 memory 变化都能被 trace 或 CLI 查到来源。

### 验收标准

- `minicode memory list --query pytest` 能显示更完整元信息。
- 新增 stale 或 conflict 行为有测试。
- Agent run 的 trace 中能看到 memory recall 原因。

## Day 5：Benchmark 任务扩展

### 实现内容

新增 benchmark 任务：

- 重构任务：要求行为不变且测试通过。
- 安全任务：验证危险命令被拒绝。
- 外接 skill 任务：验证 workspace skill 能影响路由。
- CLI 文档任务：验证 release polish 能力。
- 长上下文任务：进一步压测 compression。

### 设计重点

- 每个任务要有 expected outcome、category、tags、difficulty。
- 能自动判断的任务优先加 success command。
- 保留 `--config all` 对比能力。

### 验收标准

- `minicode eval examples/tasks --config baseline` 可运行。
- `minicode eval examples/tasks --config all` 继续生成 Markdown、JSON、CSV 报告。
- V1.1 新任务至少 5 个。

## Day 6：安全与回归检查

### 实现内容

- 增加 dirty worktree 提示。
- 写文件前支持 diff preview 或 trace 中保存更清楚的变更摘要。
- 扩展危险命令规则。
- 检查 `.env`、密钥、SSH 文件等敏感路径保护。
- 将意图保护规则做成可配置规则表：追加、覆盖、创建、删除、编辑等意图通过 `ToolSpec.intents` 匹配，而不是散落在工具执行逻辑里。
- 将敏感路径、工作区越界、危险命令、重复执行等拦截都纳入统一 policy/guard 体系，并保证每个拦截都有 reason 和测试。
- 对“读写同一文件多步操作”“先读后改”“重复失败重试”等流程增加专门回归，防止 agent 日常对话或简单文件任务卡死。

### 设计重点

- 安全策略集中在 permission/tool executor 层，不分散到各工具。
- 不做不可解释的“智能拦截”，每次 deny 都要有 reason。
- 保持 Windows 命令和跨平台命令都能被测试覆盖。
- AgentLoop 只编排流程，不承载具体工具知识；新增工具能力时优先扩展工具声明和统一 guard。

### 验收标准

- 危险命令测试覆盖新增规则。
- 敏感路径写入或读取符合预期策略。
- 权限相关 trace 清晰记录 allow/ask/deny。

## Day 7：V1.1 打磨与发布材料

### 实现内容

- 更新 README 的 V1.1 能力说明。
- 更新 demo 命令。
- 增加 V1.1 release checklist。
- 跑全量测试和关键 eval。
- 整理 V1 -> V1.1 的变化摘要。

### 验收标准

- `python -m pytest -q` 通过。
- `minicode chat --workspace . --no-model --preview` 可运行。
- `minicode skills route` 能覆盖新增 skill。
- `minicode eval examples/tasks --config baseline` 可运行。
- docs 中说明 V1.1 新增能力、使用方式和剩余限制。

## 优先级排序

如果时间不足，优先级如下：

1. 内置 skills 扩展。
2. `apply_patch`、formatter、linter 等工具增强。
3. CLI `/status`、tool call 摘要。
4. Memory 可解释性。
5. Benchmark 扩展。
6. 安全策略补强。
7. 发布材料。

## 后续可替换的硬编码点

这些位置当前可以保留，因为它们属于启发式规划、CLI 显示或示例文本，不是横切流程策略。但后续如果继续扩展工具数量或任务类型，需要优先考虑封装，避免再次出现“每加一个工具就改一处流程判断”的问题。

- RuleBasedPlanner 的默认工具选择：`agent/planner.py` 里仍显式选择 `read_file`、`list_files`、`spawn_subagent`。短期作为无模型 fallback 可以保留；后续可以改成基于工具能力标签选择，例如 `ToolSpec.capabilities=["inspect_file", "list_workspace", "delegate_review"]`。
- AgentLoop 的无 subagent fallback：`agent/loop.py` 在 subagent 禁用时手动回退到 `read_file` 或 `list_files`。短期可保留；后续可以抽成 `FallbackPlanner` 或工具能力查询。
- subagent 的 planned_actions：`subagents/runner.py` 仍按 reviewer/explorer 明确返回 `git_diff`、`git_status`、`read_file`、`search_code`、`list_files`。这属于角色任务策略，短期可保留；后续可以用 role + tool capability 生成动作计划。
- CLI 工具参数映射：`cli/app.py` 仍把 `path`、`pattern`、`content`、`old_text`、`new_text` 等参数显式列出。短期有利于 Typer help 和稳定 CLI；后续如果工具 schema 成熟，可以做动态参数解析。
- planning prompt 示例：`models/prompts.py` 里仍用 `read_file README.md` 作为固定示例。短期可以保留；后续可以根据 registry 中的安全只读工具动态生成示例。
- direct chat 关键词规则：`cli/live_ui.py` 和 `models/parser.py` 里仍有问候、工具、读写文件等关键词列表。短期可保留；后续可抽成 intent rules 配置或小型 intent classifier，并配回归用例。

## 不做的事情

V1.1 暂不做：

- 大规模重写 AgentLoop。
- 引入复杂多模型调度系统。
- 引入向量数据库。
- 做完整插件市场。
- 做 Web UI。
- 把 subagent 改成完全自治 peer agent。

这些更适合放到 V1.2 或 V2。
