# MiniCode Agent V1.2 迭代文档

## 版本定位

V1.2 是 MiniCode Agent 在较长时间停止迭代前的简历交付版。目标不是继续堆叠零散功能，而是把 V1.1 已经具备的本地 Coding Agent Runtime 收口成一个更完整、更安全、更适合面试讲述的 AI Coding Agent 项目。

V1.2 的项目定位：

> 参考 Claude Code 架构设计并实现本地 AI Coding Agent Runtime，基于 Query Loop、Tool Calling、Skill Routing、Memory System、Context Compression、Agent Team 和安全审查机制，构建可观测、可评测、可控的多任务代码 Agent 执行环境。

V1.2 的核心目标：

- 让项目能力基本对齐简历描述，重点补齐 Agent Team、Git Worktree 隔离执行、Prompt Injection 防御、安全审查和复杂任务协作闭环。
- 把 V1.1 的能力从“可运行”提升到“可展示、可解释、可评测、可写进简历”。
- 保持本地运行和工程可控，不扩展到 SaaS、插件市场、Web UI 或复杂线上系统。

## 从 V1.1 到 V1.2 的差距

V1.1 已经把项目从基础 Agent Runtime 推进到可扩展、可观测、可评测的状态，但它更像“工程能力已经打开”的版本。V1.2 的重点是把这些能力组织成面试能讲清楚的完整系统，而不是继续平均扩展所有模块。

当前差距：

- Agent Team 仍偏 explorer/reviewer 辅助能力，缺少中心化团队调度、角色契约、证据契约和安全 reviewer 闭环。
- Worktree 目前只做 git 状态探测和隔离计划记录，还没有形成“创建隔离工作区-子 Agent 执行-生成 patch/report-主 Agent 审核”的受控链路。
- 安全系统已经覆盖权限、危险命令、敏感路径和 trace redaction，但还缺少 Prompt Injection 这种语义层攻击的明确建模和 benchmark。
- Memory 已经有召回和沉淀基础，但 admission policy、failure memory、conflict/stale 和 recall evidence 还需要进一步产品化。
- Context compression 已经能缓解长上下文问题，但需要围绕 evidence refs、trace refs、prompt segment 和 reviewer 证据保留形成更强解释性。
- Skill 系统已具备 metadata-driven routing，但还需要 doctor、schema 治理、候选解释和覆盖关系说明，让它更像能力平台而不是 prompt 文件集合。
- Eval 已能做 ablation 和回归，但 V1.2 需要把安全、协作、记忆、压缩这些亮点变成可量化 demo 和报告。

V1.2 的判断标准：如果某项能力不能被 demo、trace、benchmark 或文档证明，就不算真正完成。

## 简历对齐目标

V1.2 完成后，项目应能支撑以下简历级表述。

### Skill 能力体系

目标：把 Skill 从“路由到提示词”升级为“可治理的任务能力体系”。

应具备：

- Skill metadata schema、版本、校验和错误提示。
- Skill Router 支持候选召回、得分解释、rerank fallback 和 no-match reason。
- Skill 内容按工作流组织，而不是普通 prompt 文案。
- CLI 和 trace 能展示 skill 选择原因、候选差异和 rerank 决策。

简历表述方向：

- 设计 Skill 分层路由系统，将原子 Tool、高层 Skill 与 Skill 目录分层组织，结合任务意图识别、元信息标签、适用边界与示例进行召回和精排，降低 Skill 自进化增长下的检索噪声、功能重叠和 Token 成本。

### 自进化记忆沉淀

目标：让 Memory System 从“保存记录”升级为“可审计的经验沉淀闭环”。

应具备：

- Memory admission policy 独立于持久化 Store。
- 区分 project memory、user memory、failure memory、workflow memory。
- 记录 recall reason、source run id、confidence、admission reason 和 stale/conflict 状态。
- 支持错误修复经验、项目偏好、技能成长信号的沉淀和复用。

简历表述方向：

- 设计自进化记忆沉淀机制，将执行过程中的程序性经验、情景记忆、用户画像自动提炼为可复用记忆资产，构建“执行-反思-提炼-分类存储-索引更新-按需复用”的闭环，实现跨会话复用、错误修复加速和 Skill 能力生长。

### 分层上下文压缩

目标：让 Context Compression 从“截断长上下文”升级为“证据保留型上下文管理”。

应具备：

- 分离 raw observation、structured facts、evidence refs 和 final summary。
- 对工具结果、diff、测试输出、trace 事件使用不同压缩策略。
- 保留关键路径、失败原因、工具输出摘要和 reviewer evidence。
- 支持 Prompt Cache 或 Prompt Segment 的设计说明，即使 V1.2 不接真实缓存服务，也要保留清晰边界。

简历表述方向：

- 设计分层上下文压缩机制，将大工具结果外置化、缓存友好型占位压缩与结构化笔记摘要结合，构建“摘要预览-占位替换-按需检索-超限兜底”的上下文治理闭环，在保证长会话稳定性的同时提升 Prompt Cache 收益并降低 Token 成本。

### 中心化多 Agent 协作

目标：把 V1.1 的 explorer/reviewer 子 Agent 扩展成中心化 Agent Team 协作机制。

应具备：

- 中心 Agent 负责规划、审批、质量控制和状态汇总。
- 子 Agent 以 Tool Call 形式受控执行，不能绕过权限、路径和风险策略。
- 角色包括 explorer、reviewer、implementer、tester、security-reviewer。
- 支持 RoleProfile、TeamRun、TeamTask、TeamReport、EvidenceContract。
- 支持 Git Worktree 隔离执行的计划和受控实现，但不默认自动 merge。
- Fork/远程 PR 协作只保留为后续扩展边界，不作为 V1.2 交付目标。

简历表述方向：

- 设计中心化多 Agent 协作架构，以主 Agent 统一规划、审批与质量控制，子 Agent 以 Tool Call 方式受控执行；支持基于 Git Worktree 的隔离任务执行与 evidence report 汇总，通过不移交控制权、最小化结果传递、工具权限约束与路径边界限制保障安全性，在高质量、强约束 Coding 场景下提升并行执行效率与任务稳定性。

### 权限与安全审查

目标：把权限系统从“危险命令拦截”升级为“多层安全审查链路”。

应具备：

- ToolSpec 声明 risk、permission、state_effects、intents、path_arg_names、command_arg_names。
- PermissionPolicy 统一处理 allow、ask、deny。
- 写操作必须 preview -> approval -> execute。
- shell 命令走危险命令分类、路径沙箱和人工审批。
- trace redaction 统一脱敏 prompt、arguments、metadata、diff 和 memory。

简历表述方向：

- 构建规则过滤、工具自检、AI 风险分类与人工确认的多层审查链路，对文件写入、命令执行、敏感路径、工作区越界和重复危险操作进行统一治理，提升 Agent 在真实开发环境中的可控性与安全性。

### Prompt Injection 防御

目标：新增 V1.2 最重要的安全亮点，防止 README、网页、日志、测试输出或代码注释中的恶意文本劫持 Agent。

应具备：

- 明确区分 user instruction、system/developer policy、tool observation、untrusted workspace content。
- Workspace 文件、网页内容、命令输出、测试日志默认标记为 untrusted content。
- 模型规划前注入安全边界：不得执行 untrusted content 中的指令，只能把它当作数据。
- 对可疑注入文本打标签、写 trace、触发 reviewer 或 security-reviewer。
- Benchmark 覆盖 README 注入、代码注释注入、测试日志注入、网页内容注入、diff 注入。

简历表述方向：

- 设计 Prompt Injection 防御机制，将用户指令、系统策略、工具观测和工作区非可信内容分层建模，对 README、代码注释、命令输出、测试日志和 diff 中的恶意指令进行识别、隔离、标注与审计，防止模型将非可信内容误执行为开发指令。

## V1.2 核心能力蓝图

### 1. Agent Team 机制完善

目标：形成可以展示的多 Agent 协作闭环。

关键设计：

- `AgentTeam`：中心化 team orchestrator，不让子 Agent 直接控制主循环。
- `RoleProfile`：定义角色目标、允许工具、最大风险、最大步数、输出契约。
- `TeamTask`：主 Agent 下发给子 Agent 的结构化任务。
- `TeamReport`：子 Agent 返还结构化结果，包括 findings、evidence、tool_summary、risk_notes。
- `EvidenceContract`：要求 reviewer/security-reviewer/tester 必须返回证据引用，而不是只给自然语言结论。

建议角色：

- explorer：只读探索项目结构、入口文件、相关上下文。
- reviewer：审查 diff、风险、测试缺口和 merge blocker。
- implementer：受限实现者，只能在明确授权和审批链路下生成 patch proposal，默认不直接写入。
- tester：选择并运行最小验证命令，汇总失败原因。
- security-reviewer：检查 prompt injection、敏感路径、危险命令和权限边界。

验收标准：

- `spawn_subagent` 支持 role profile。
- trace 中有 `team_started`、`team_role_started`、`team_role_completed`、`team_finished`。
- reviewer 输出包含 `changed_files`、`risks`、`test_suggestions`、`evidence`、`merge_blockers`。
- Agent Team benchmark 中 full 配置通过，baseline 允许作为 ablation 对照失败。

### 2. Git Worktree 隔离执行

目标：让复杂任务可以在隔离工作区中探索、实现和验证，避免直接污染用户当前 workspace。

关键设计：

- `WorkspaceIsolationPlan`：从 V1.1 的只读计划升级为可执行计划，记录 source branch、dirty state、worktree path、created branch、cleanup policy。
- `WorktreeManager`：封装 `git worktree add/remove/list`，统一处理路径、命名、清理和失败回滚。
- `IsolatedTeamTask`：主 Agent 将可隔离任务下发到 worktree，子 Agent 在隔离目录运行，但仍复用 ToolSpec、PermissionPolicy、trace 和安全审查。
- `PatchProposal`：隔离工作区不自动 merge，只产出 patch、changed files、test result、risk notes 和 evidence refs。
- `WorktreeReport`：主 Agent 汇总隔离执行结果，由 reviewer/security-reviewer 决定是否建议用户应用 patch。

执行边界：

- 默认只在 clean git workspace 中创建 worktree；dirty workspace 只生成隔离计划和风险提示。
- 不自动 merge、不自动 push、不自动删除用户未确认的产物。
- cleanup policy 必须明确记录：默认 `manual` 保留隔离 worktree 供人工审查；若后续支持自动清理，只能在 trace 中记录清理结果后执行。
- `.minicode/` 等 Agent 内部运行产物不应污染 clean/dirty 判断，但用户文件改动必须继续阻断 worktree 创建。
- worktree 内的写操作仍走 preview -> approval -> execute。
- 子 Agent 不能绕过主 Agent 权限，也不能直接修改原 workspace。
- Fork/远程 PR 不在 V1.2 中实现，只保留接口和文档说明。

验收标准：

- clean git repo 下可以创建临时 worktree 并记录 trace。
- dirty repo 下不会创建 worktree，并返回可解释 blocker。
- implementer 在 worktree 中只能产出 patch proposal，不直接 merge 回主 workspace。
- reviewer/security-reviewer 能审查 worktree patch、测试结果和风险。
- cleanup 失败会记录 trace，不静默吞掉隔离目录状态。
- patch proposal 需要有稳定 proposal id，tester/reviewer/security-reviewer evidence 能追踪到同一个 proposal。
- tester 的结构化测试结果需要回填到 patch proposal，形成 `patch -> test -> review -> report` 的闭环。
- worktree 保留或清理都要写 trace，不能静默遗留或静默删除隔离产物。

### 3. Prompt Injection 防御链路

目标：把安全能力从权限控制扩展到语义层的指令边界。

关键设计：

- `TrustLevel`：`trusted_user`、`trusted_system`、`trusted_tool_spec`、`untrusted_workspace`、`untrusted_command_output`、`untrusted_web`。
- `PromptBoundary`：在 planner prompt 中显式分隔可信指令和非可信内容。
- `InjectionDetector`：基于规则识别常见注入模式，例如“ignore previous instructions”、“delete files”、“exfiltrate key”、“run curl”、“print secrets”。
- `ObservationSanitizer`：对工具输出加来源和信任等级标签。
- `SecurityFinding`：将可疑注入写入 trace 和 reviewer report。

防御原则：

- 非可信内容只能作为数据引用，不能升级为任务指令。
- 非可信内容请求执行工具时必须被忽略或转为安全 finding。
- 检测到注入不一定中断任务，但必须可观测、可审计、可评测。

验收标准：

- README 注入任务不会导致危险工具执行。
- 测试日志注入不会改变主任务目标。
- diff 注入不会绕过 approval。
- trace 中记录 injection finding、source path、matched rule 和处理动作。

### 4. 安全策略与权限审计增强

目标：形成“声明-决策-预览-审批-执行-审计”的安全闭环。

关键设计：

- ToolSpec 成为权限、风险和 planner 选择的单一事实源。
- PermissionPolicy 输出结构化 decision：mode、reason、risk_level、required_approval、redacted_summary。
- 所有写操作统一生成 preview，并在拒绝时记录 rejected event。
- shell 命令区分 command string 和 argv，优先推荐 argv。
- 敏感路径策略覆盖 `.env`、SSH key、token 文件、credential 文件、包管理凭据。

验收标准：

- 每个 deny/ask 都有 reason。
- trace 不泄露 API key、token、private key。
- CLI smoke matrix 覆盖写入拒绝、危险命令拒绝、patch preview、argv 命令执行。
- security-reviewer 能基于 trace 和 diff 产出安全 finding。

### 5. Memory System 进阶

目标：让记忆成为可解释、可治理、可复用的项目资产。

关键设计：

- 拆出 `memory/policy.py`：admission、secret check、conflict detection、stale policy、recall scoring。
- MemoryStore 专注持久化和查询。
- MemoryReflectionEngine 专注候选生成。
- Recall 返回 reason 和 evidence，而不是只返回内容。
- 支持 memory compaction，避免长期运行后记忆噪声过大。

验收标准：

- memory add/list/stale/delete/search 全链路测试通过。
- recall trace 记录 query、record id、score、reason。
- conflicting memory 有可解释提示。
- failure memory 能被后续相似失败任务召回。

### 6. Context / Prompt Cache / Evidence Compression

目标：让长任务上下文稳定，并能解释压缩依据。

关键设计：

- `ContextFrame`：表示一次模型输入的分层上下文。
- `EvidenceRef`：引用文件、trace event、tool observation、diff hunk。
- `CompressionPolicy`：决定保留原文、摘要、证据引用还是外置缓存。
- `PromptSegment`：为未来 prompt cache 预留稳定段和动态段。

验收标准：

- 长输出触发 compression 后保留关键路径、失败原因和证据引用。
- reviewer findings 不因 compression 丢失 evidence。
- trace 记录 compression ratio、fallback、kept refs。
- benchmark 覆盖长日志、长 diff、长文件摘要。

### 7. Skill 系统产品化

目标：Skill 能作为项目能力体系展示，而不是内部 prompt 目录。

关键设计：

- metadata schema 固化并文档化。
- skill registry 支持 source、version、priority、override reason。
- skills route 输出 top candidates、selected reason、unselected reason。
- 可增加 `skills doctor` 检查 metadata、SKILL.md、aliases、examples。

验收标准：

- 内置 skill 都有 metadata schema version。
- workspace skill 覆盖内置 skill 时有 trace/CLI 提示。
- broken skill metadata 给出可读错误。
- release-polish/security-review/repo-onboarding/refactoring 均有 route 测试。

### 8. Eval & Regression Dashboard

目标：把项目能力变成可量化结果，便于简历和面试说明。

关键设计：

- benchmark 覆盖安全、memory、context、team、skills、CLI、prompt injection。
- all config 对比 baseline、skill_only、memory_skill、full、full_llm_memory。
- report 输出 pass rate、工具调用、retry、memory 写入、compression、subagent 调用和安全 finding。
- 生成简短 release summary，方便贴进 README 或面试材料。

验收标准：

- `python -m pytest -q` 通过。
- `minicode eval examples/tasks --config all` 生成 Markdown、JSON、CSV。
- full/full_llm_memory 在 V1.2 关键任务上通过率显著高于 baseline。
- prompt injection benchmark 有明确 pass/fail 判断。

### 9. CLI / Demo / 简历展示材料

目标：让项目能被快速演示和讲清楚。

关键设计：

- CLI 保持轻量，不做复杂 TUI。
- `/status`、`/trace`、`/memory`、`/skills`、`/diff`、`/tools`、`/config`、`/last` 保持稳定。
- 新增 demo 脚本：安全拒绝、prompt injection 防御、Agent Team review、worktree 隔离执行、memory recall、context compression。
- 修复 README 编码和结构，让文档能直接支撑简历。
- 面试问答补充 V1.2 设计取舍。

验收标准：

- demo commands 可复制运行。
- README 无乱码，能说明 V1.2 能力、限制和运行方式。
- docs 中有架构、security、demo、interview Q&A。
- 简历亮点能从文档中直接提炼。

## 四天迭代节奏

V1.2 只有四天节奏，每天都应形成一个能展示的能力闭环。由于实际开发可能很久之后才开始，这里的“天”表示工作包顺序，而不是必须连续执行的日历时间。

### Day 1：Prompt Injection 防御与安全审计闭环

目标：优先补齐最适合简历展示的安全能力。

当天交付物：

- 一个 prompt injection benchmark suite。
- 一套 TrustLevel / PromptBoundary / InjectionFinding 数据结构。
- 一条能展示“恶意 README 或日志不会劫持 Agent”的 demo。
- 一份 trace evidence，能说明注入来源、匹配规则和处置动作。

实现内容：

- 引入 TrustLevel 和 PromptBoundary。
- 对 read_file、search_code、run_shell、run_tests、git_diff 等 observation 标记信任等级。
- 实现 InjectionDetector 规则集。
- 在 planner prompt 中明确非可信内容边界。
- 将 injection finding 写入 trace。
- 扩展 security-reviewer 输出结构。

验收标准：

- README prompt injection benchmark 通过。
- command output injection benchmark 通过。
- diff injection benchmark 通过。
- 危险命令不被注入内容触发。
- trace 展示 injection finding 和处置动作。

推荐新增测试：

- `test_prompt_injection_readme_is_data_not_instruction`
- `test_prompt_injection_from_command_output_is_ignored`
- `test_prompt_injection_in_diff_cannot_bypass_approval`
- `test_security_reviewer_reports_injection_finding`

### Day 2：Agent Team 与 Worktree 隔离执行

目标：把 Agent Team 做成中心化、多角色、可审计的协作架构，并让复杂任务可以在 Git Worktree 中隔离执行。

当天交付物：

- 一个中心化 Agent Team orchestrator。
- explorer、reviewer、tester、security-reviewer 的 RoleProfile。
- 结构化 TeamReport 和 EvidenceContract。
- 一套 WorktreeManager / WorkspaceIsolationPlan / PatchProposal 结构。
- 一条能展示“主 Agent 调度团队在隔离 worktree 中完成实现、测试、审查，最后只返回 patch proposal”的 demo。

实现内容：

- 定义 RoleProfile、TeamTask、TeamReport、EvidenceContract。
- 扩展 explorer/reviewer，新增 tester/security-reviewer。
- implementer 先以 patch proposal 形式存在，不默认直接写入。
- Team orchestrator 统一调度角色、收集报告、合并 evidence。
- 将 V1.1 的 workspace isolation plan 升级为可执行 Git Worktree 隔离链路。
- clean repo 允许创建临时 worktree，dirty repo 返回 blocker 和风险说明。
- worktree 内执行结果只生成 patch proposal、test result、risk notes 和 evidence refs。
- trace 记录 team lifecycle。
- eval 增加 team assertions。

验收标准：

## 可直接提炼进简历的技术亮点

- 设计 Skill 分层路由系统，将原子 Tool、高层 Skill 与 Skill 目录分层组织，结合任务意图识别、元信息标签、适用边界和示例进行召回与精排，降低 Skill 增长下的检索噪声、功能重叠和 Token 成本。
- 设计自进化记忆沉淀机制，将执行过程中的程序性经验、情景记忆、用户画像和失败修复经验沉淀为可复用记忆资产，形成“执行-反思-提炼-分类存储-索引更新-按需复用”的闭环。
- 设计分层上下文压缩机制，将大工具结果外置化、缓存友好型占位压缩与结构化 evidence refs 结合，在保证长会话稳定性的同时降低 Token 成本并提升 Prompt Cache 收益。
- 设计中心化多 Agent 协作架构，由主 Agent 统一规划、审批和质量控制，子 Agent 以 Tool Call 方式受控执行，通过最小权限、路径边界、证据契约和结果汇总提升复杂 Coding 任务的稳定性。
- 设计基于 Git Worktree 的隔离执行机制，将复杂实现任务放入临时工作区运行，产出 patch proposal、测试结果和审查 evidence，避免子 Agent 直接污染用户当前 workspace 或自动 merge。
- 构建权限与安全审查链路，结合规则过滤、工具自检、Prompt Injection 检测、AI 风险分类和人工确认，对文件写入、命令执行、敏感路径、工作区越界和非可信内容注入进行统一治理。

## 面试讲述路径

建议面试时不要按“我做了很多模块”来讲，而是按一个复杂任务如何被安全完成来讲。

推荐叙事：

1. 项目本质是本地 Coding Agent Runtime，不是简单 prompt wrapper。用户任务进入 Query Loop 后，模型只能请求注册工具，真实文件写入、命令执行和子 Agent 调用都要经过 ToolSpec、PermissionPolicy、preview approval 和 trace。
2. 为了解决复杂任务上下文不足的问题，引入 Skill Routing、Memory System 和 Context Compression：Skill 负责选工作流，Memory 负责跨会话经验复用，Context Compression 负责长任务中保留关键 evidence。
3. 为了解决单 Agent 复杂任务质量不稳定的问题，引入中心化 Agent Team：主 Agent 保留控制权，子 Agent 以受限 Tool Call 执行 explorer、reviewer、tester、security-reviewer 等角色，并通过 EvidenceContract 返回可审计结果。
4. 为了避免复杂实现任务污染当前 workspace，引入 Git Worktree 隔离执行：clean repo 中创建临时 worktree，implementer 只产出 patch proposal，tester/reviewer/security-reviewer 审查后由主 Agent 汇总，不自动 merge。
5. 为了解决真实仓库中的安全风险，引入多层安全链路：权限策略处理路径和命令风险，Prompt Injection 防御处理 README、日志、diff、网页内容中的非可信指令，trace redaction 防止敏感信息泄露。
6. 最后用 eval 和 demo 证明效果：baseline、skill_only、memory_skill、full 等配置对比，报告展示通过率、工具调用、memory recall、compression、subagent 调用、worktree patch proposal 和 security finding。

面试中可以重点展示三条 demo：

- 安全 demo：README 或测试日志里包含恶意指令，Agent 将其识别为 untrusted content，只记录 finding，不执行危险命令。
- 协作 demo：主 Agent 调度 explorer/reviewer/security-reviewer/tester 完成一次代码审查，最终报告包含 evidence 和 merge blocker。
- 隔离执行 demo：clean repo 中创建 worktree，implementer 生成 patch proposal，tester/reviewer/security-reviewer 审查，主 workspace 不被自动修改。
- 记忆与压缩 demo：第一次失败修复沉淀 failure memory，第二次相似任务召回；长日志被压缩后 reviewer evidence 仍可追踪。

## 不做的事情

V1.2 明确不做：

- 不做 Web UI 或 SaaS 平台。
- 不做完全自治 peer agents。
- 不实现自动 fork、远程 PR、自动 merge 或 push。
- 不引入复杂多模型调度系统。
- 不引入向量数据库作为主路径。
- 不把所有安全判断交给 LLM。
- 不为了简历效果牺牲本地可控性和可测试性。

这些方向可以作为 V2 或独立项目，而不是 V1.2 的交付范围。
