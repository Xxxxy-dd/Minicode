# MiniCode Agent 面试问答

这份文档按 MiniCode Agent 当前已实现的技术亮点整理面试官可能追问的问题和参考回答。回答重点放在设计取舍、实现细节、风险控制和后续扩展，而不是只背概念。

## 1. Tool Runtime 与统一工具协议

### 问题 1：为什么先做 Tool Runtime，而不是一开始就接 LLM 做 Agent Loop？

回答：

Coding Agent 的核心不是模型聊天，而是模型能否可靠地观察和操作开发环境。如果直接接 LLM，很容易变成 prompt demo，缺少工程边界。我先抽象了 `ToolSpec`、`ToolObservation`、`BaseTool` 和 `ToolRegistry`，把文件读取、代码搜索、git 状态等能力封装成统一工具接口。

这样后续无论是 CLI、Agent Loop、Skill 还是 Subagent，都可以复用同一套工具协议。第一阶段先做只读工具，是为了让 Agent 先具备稳定观察能力，再逐步开放写入和命令执行，降低早期风险。

### 问题 2：`ToolObservation` 为什么要结构化，而不是直接返回字符串？

回答：

Agent 后续需要根据工具结果做判断，比如工具是否成功、错误原因是什么、输出是否被截断、命令 exit code 是多少。如果只返回字符串，模型和上层系统都很难稳定解析。

所以我让工具统一返回 `ToolObservation`，包含：

- `ok`
- `output`
- `error`
- `metadata`
- `truncated`

这样 Trace Store、Agent Loop、Harness 都可以直接消费结构化结果。

### 问题 3：为什么用 `ToolRegistry`？

回答：

`ToolRegistry` 解决的是工具发现和统一执行入口的问题。所有工具都通过 registry 注册和查找，避免 CLI、Agent Loop、Subagent 各自维护工具列表。后续做权限控制、Skill 注入、Subagent 工具限制时，也可以基于 registry 做过滤。

## 2. 权限系统与路径沙箱

### 问题 1：你的权限系统怎么防止 Agent 读取或修改 workspace 外的文件？

回答：

我实现了 `PathSandbox`，所有工具执行前都会通过 `ToolExecutor` 进入 `PermissionPolicy`。权限层会检查 `path`、`target_path`、`file_path` 等路径参数，将它们 resolve 成绝对路径后判断是否仍在 workspace 内。

如果路径通过 `../` 等方式逃逸到 workspace 外，权限层会直接返回 `DENY`，工具不会执行。这个判断发生在工具执行前，而不是依赖每个工具自己小心处理。

### 问题 2：为什么权限判断放在 `ToolExecutor`，而不是放在每个 Tool 里面？

回答：

权限判断如果分散在每个 Tool 里，后续新增工具时很容易漏掉，安全边界也不统一。我把它收敛到 `ToolExecutor`，让所有工具调用都必须经过同一个入口：

```text
Tool request
-> PermissionPolicy
-> allow / ask / deny
-> Tool execution
```

工具内部仍然保留自己的参数校验，形成双层保护，但核心安全策略由统一网关负责。

### 问题 3：`ALLOW / ASK / DENY` 是怎么设计的？

回答：

我把权限结果分成三类：

- `ALLOW`：低风险或只读操作可以直接执行。
- `ASK`：写文件、执行命令等中高风险操作需要用户确认。
- `DENY`：路径逃逸、危险命令、被禁止工具直接拒绝。

这样既能支持自动化，也不会让 Agent 默认拥有过大的执行权限。

## 3. 写入工具与变更控制

### 问题 1：Agent 写文件时怎么避免误改项目？

回答：

写入工具默认不是 `ALLOW`，而是 `ASK`。`write_file` 和 `edit_file` 都必须显式 approval 才会执行。

`edit_file` 使用精确字符串替换。如果 `old_text` 找不到，会拒绝执行；如果匹配多次且没有显式 `replace_all`，也会拒绝执行。这样可以避免模型以为只改一处，实际改了多处。

### 问题 2：为什么 `write_file` 默认不自动创建父目录？

回答：

自动创建父目录虽然方便，但对 Agent 来说有风险。模型可能把路径写错，例如：

```text
src/minicode_agnet/...
```

如果工具自动创建目录，就会悄悄产生错误结构。所以我让 `write_file` 默认拒绝缺失父目录，只有显式传入 `create_parents=true` 时才创建。这个设计牺牲了一点便利性，但换来更强的可控性。

### 问题 3：为什么要记录 `before_hash` 和 `after_hash`？

回答：

写入工具不仅要完成修改，还要能被审计和回放。我在 metadata 里记录 `before_hash`、`after_hash`、`before_chars`、`after_chars`，后续 Trace Store 可以记录每次写入前后的状态。

这样面试时可以讲清楚：系统不是“黑箱改文件”，而是能追踪每次变更的输入、输出和文件状态变化。

## 4. Shell / Test 工具与命令安全

### 问题 1：Shell 工具风险很高，你是怎么控制的？

回答：

我把 `run_shell` 和 `run_tests` 都设置成 `ASK` 权限，默认不会执行，必须显式 approval。即使用户批准，命令仍然会先经过 `CommandSafetyClassifier`。

目前会拦截：

- `rm -rf`
- `del /s` / `del /q`
- `rmdir /s`
- `format`
- `diskpart`
- `shutdown`
- `reboot`
- `git push`
- `curl | ...`
- `.env` 外传相关模式

如果命中危险规则，会直接 `DENY`，即使传了 `approved=True` 也不会执行。

### 问题 2：为什么 `run_shell` 使用 `shell=False`？

回答：

`shell=True` 会把命令交给系统 shell 解释，容易引入 shell 注入、管道、重定向等额外风险。`shell=False` 要求我们传入明确的 argv，执行边界更清晰。

CLI 里我也支持多次 `--arg`：

```powershell
minicode tools run run_shell --arg cmd --arg /c --arg "echo hello" --approved
```

这样复杂命令不需要依赖字符串解析，Windows 下也更稳定。

### 问题 3：为什么还保留 `--command`？

回答：

`--command` 对简单命令更方便，比如 demo 或手动调试：

```powershell
minicode tools run run_shell --command "cmd /c echo hello" --approved
```

但系统内部和测试更推荐使用 `argv`。权限层也会同时检查 `command` 和 `argv`，防止通过 `argv=["git","push"]` 绕过危险命令检测。

### 问题 4：`run_tests` 和 `run_shell` 有什么区别？

回答：

`run_shell` 是通用命令执行工具，风险更高，默认 timeout 较短。`run_tests` 是面向验证阶段的专用工具，默认执行当前 Python 环境下的：

```text
python -m pytest
```

它仍然需要 approval，但语义上更适合 Agent Loop 的 `VERIFY` 阶段。后续可以给 `run_tests` 增加 test path、keyword、失败摘要等专门能力。

## 5. 安全边界与可扩展性

### 问题 1：目前权限系统还有哪些不足？

回答：

当前版本是 MVP 权限系统，已经覆盖路径沙箱、工具风险等级、approval flow 和危险命令拦截。但它仍然有提升空间：

- 路径参数目前主要检查固定字段，未来需要支持递归检查复杂 schema。
- 命令安全分类基于规则，后续可以加入更细粒度 parser 或策略配置。
- approval 当前是布尔值，后续可以变成带审批人、时间、理由的结构化事件。
- 还没有完整 Trace Store，无法持久化每次权限决策。

这些正好对应后续 Trace、Agent Loop 和 Harness 的建设方向。

### 问题 2：你怎么证明这些安全控制真的生效？

回答：

我给关键路径都写了测试：

- workspace 外路径会被拒绝。
- `write_file` 未批准不会写入。
- `edit_file` 多重匹配默认拒绝。
- `run_shell` 未批准不会执行。
- `rm -rf`、`git push` 等危险命令即使 approved 也会被拒绝。
- `argv=["git","push"]` 也会被拦截，避免绕过 `command` 字符串检测。

当前测试覆盖的是单元和 CLI 层面，后续 Harness 会把这些能力放进 benchmark 任务里做端到端验证。

## 6. Trace Store 与执行审计

### 问题 1：为什么要做 Trace Store？它解决什么问题？

回答：

Coding Agent 不是一次性函数调用，而是一连串工具调用、权限判断、观察结果和状态更新。如果没有 Trace，任务失败时很难回答“Agent 做了什么、为什么这么做、在哪一步失败”。

我实现 Trace Store 的目的有三个：

- 调试：能回放一次工具调用过程。
- 审计：能看到权限判断、工具结果和文件变更 metadata。
- 评测：后续 Harness 可以统计 tool calls、duration、失败原因等指标。

当前已经记录三类核心事件：

```text
tool_requested
permission_checked
tool_finished
```

这为后续 Agent Loop 的 `run_started`、`phase_changed`、`model_request`、`run_finished` 等事件打基础。

### 问题 2：Trace 里具体记录了什么？

回答：

一次工具调用至少会记录：

- 请求的 tool 名称。
- 清理后的 arguments。
- 是否 approved。
- 权限判断结果和原因。
- tool call id。
- 执行是否成功。
- error。
- output 字符数。
- 是否截断。
- `duration_ms`。
- 工具 metadata，例如文件 hash、exit code、permission reason。

例如写文件工具会记录 `before_hash` 和 `after_hash`，命令工具会记录 `exit_code` 和 timeout 信息。这样后续不需要重新解析文本输出，也能做审计和统计。

### 问题 3：为什么 Trace payload 要过滤 `None` 和默认参数？

回答：

最初 trace 会记录 CLI 传入的所有参数，包括很多无关字段，例如 `pattern=None`、`command=None`、`replace_all=False`。这种 trace 很吵，不利于调试，也会增加后续模型阅读成本。

所以我在 CLI 构造 arguments 时做了 compact，只保留用户实际传入或有意义的参数；在 `safe_payload` 里也会过滤 `None`、空 dict 和空 list。这样 trace 更接近真实 tool call 输入。

### 问题 4：Trace 里如何避免泄露敏感信息？

回答：

我做了两层简单脱敏。

第一层是根据 key 名脱敏，如果字段名包含：

```text
secret / token / password / key
```

就记录为 `[redacted]`。

第二层是对字符串 value 做模式脱敏，例如：

```text
Authorization: Bearer ...
api_key=...
OPENAI_API_KEY=...
ANTHROPIC_API_KEY=...
```

这些会在写入 trace 前被替换成 `[redacted]`。这还是 MVP 版本，后续可以加入更完整的 secret scanner。

### 问题 5：为什么同时支持 SQLite 和 JSONL？

回答：

设计上优先使用 SQLite，因为它适合查询、按 run_id 过滤，也方便后续做 Harness 指标统计。但本地开发环境可能受限，比如 Windows/conda 下 `_sqlite3` DLL 可能因为权限问题加载失败。

为了让 Trace 在受限环境里也可用，我加了 JSONL fallback：SQLite 初始化失败时自动写到 `.minicode/traces/trace.jsonl`。CLI 会显示当前 backend 和存储路径：

```text
trace_backend: sqlite
trace_backend: jsonl
```

这体现的是降级能力：正式环境用 SQLite，受限环境仍然能记录和回放。

### 问题 6：`trace` 命令为什么同时提供表格和 JSON？

回答：

表格适合人快速看一次 run 的流程，例如：

```text
time | run | event | tool | ok | reason
```

但完整分析、调试和后续 Harness 需要结构化数据，所以我加了：

```powershell
minicode trace <run_id> --json
```

它会输出完整事件 JSON。这样人和程序都能消费同一份 trace。

### 问题 7：`RuntimeContext` 的作用是什么？

回答：

一开始 CLI 直接创建 `TraceStore` 和 `run_id`，短期能跑，但后续 Agent Loop、Subagent、Harness 都需要共享这些运行上下文。如果每个模块自己创建，run_id 和 trace 会很分散。

所以我加了 `RuntimeContext`，统一管理：

```text
workspace
run_id
trace_store
```

后续 Agent Loop 只需要持有一个 RuntimeContext，就可以把所有阶段和工具调用写入同一次 run。

## 7. 面向后续 Agent Loop 的设计

### 问题 1：这些工具如何接入后面的 Agent Loop？

回答：

后续 Agent Loop 不会直接调用具体函数，而是通过 `ToolExecutor` 调用工具。流程会是：

```text
Model requests tool call
-> ToolRegistry 查找工具
-> PermissionPolicy 做安全判断
-> ToolExecutor 执行
-> ToolObservation 返回给 Agent
-> Trace Store 记录事件
```

这样模型只负责提出工具调用意图，真正执行由 Runtime 控制。Trace Store 会记录工具请求、权限判断、执行结果和耗时，后续 Agent Loop 可以在失败时根据 trace 做 replan，也可以把 trace 交给 Harness 做评测。

### 问题 2：为什么这些早期模块对简历项目很重要？

回答：

因为它们体现了 Agent 工程能力，而不是简单 API 调用。真实 Coding Agent 最难的不是让模型生成代码，而是构建一个可控执行环境：工具协议、权限边界、错误处理、命令执行、变更审计和可测试性。

这几天实现的 Tool Runtime、Permission Gateway、Write Tools、Shell Tools 和 Trace Store，就是后续 Skill、Memory、Context Compression、Subagent 和 Harness 的基础。

### 问题 3：第六天的 Agent Loop 你做了哪些关键优化？

回答：

Day 6 最初只是一个规则驱动的 loop，后来我做了几项优化：

- 抽出了 `RuleBasedPlanner`，把“选 skill、出计划、选下一步工具”从 loop 主流程中拆出去。
- 增加了 `run_started` 和 `INIT` trace，让一次 run 的生命周期更完整。
- 把 `RuntimeContext` 统一成 `workspace + run_id + trace_store`，后续 Agent Loop、Subagent、Harness 都能复用。
- 引入 `max_steps`，为 Day 7 之后的模型驱动 loop 预留安全上限。
- 让 loop 真的接触工具执行，而不是纯模拟，至少能先读 `README.md`，再 fallback 到 `list_files`。

这样 Day 6 不只是“能跑”，而且已经具备后续接模型和接 Harness 的结构基础。

## 8. Skill System 与 Skill Routing

### 问题 1：为什么要把 Skill 做成独立系统，而不是直接把提示词写死在 Agent Loop 里？

回答：
如果把调试、测试、代码审查这些能力直接写进 Agent Loop，短期能跑，但后续会很难维护。不同任务需要不同的工作流、约束和示例，例如调试任务强调先复现失败，测试任务强调先定义行为契约，代码审查任务强调先列风险和证据。

所以我把 Skill 设计成独立能力包：每个 skill 都有 `metadata.yaml` 和 `SKILL.md`。metadata 负责路由和发现，markdown 内容负责给模型注入具体工作流。这样 Agent Core 不需要知道每种任务的细节，只需要根据路由结果加载对应 skill，再注入 prompt。

### 问题 2：Skill metadata 里为什么要有 name、description、tags、applies_to、examples 和 aliases？

回答：
这些字段服务两个目标：可解释路由和后续扩展。

- `name` 是稳定标识，用于 CLI、trace 和 AgentState。
- `description` 给人看，也能作为低权重匹配信号。
- `tags` 表示粗粒度能力类别，例如 tests、review、failure。
- `applies_to` 描述适用场景。
- `examples` 表示典型任务表达。
- `aliases` 专门服务路由，包含英文别名和中文触发词，例如“测试失败”“审查”“traceback”。

这样 examples 不需要承担所有匹配职责，aliases 可以更直接地优化召回质量。

### 问题 3：Skill 路由是怎么做的？

回答：
当前是确定性 metadata-based routing。系统会把用户任务分词，然后和每个 skill 的 `name / aliases / tags / applies_to / examples / description` 做匹配。不同字段有不同权重，例如 aliases 和 name 权重更高，description 权重更低。

路由结果不是只返回一个名字，而是返回 `SkillRouteResult`：

```text
selected skills
candidates
scores
reasons
```

这些结果会写入 `AgentState.skill_candidates`、`AgentState.skill_route_reasons`，也会进入 trace 的 `skill_selected` 事件。这样面试官追问“为什么选择这个 skill”时，可以直接解释和展示证据。

### 问题 4：为什么不在 Day 10 一开始就做 LLM rerank？

回答：
我刻意先把 Day 10 做成确定性 top-k 路由，再在 Day 17 打磨阶段接入 LLM rerank。原因有三点：

第一，Skill 路由是 Agent 的基础控制面，基础版本应该稳定、可测试、可解释。关键词召回虽然简单，但每个分数和 reason 都能复现。

第二，LLM rerank 会引入模型波动和额外成本。如果基础召回还没稳定，就加 rerank，失败时很难判断是 metadata 问题、prompt 问题还是模型判断问题。

第三，后续 Memory、Context Compression、Subagent 都会改变路由上下文。等这些模块稳定后，再把 deterministic candidates 交给 LLM rerank，会更合理。

所以当前设计是：Day 10 的确定性路由负责稳定召回和可解释 reason；Day 17 的 LLM rerank 只重排已召回候选，并且没有模型或模型返回异常时回退确定性顺序。

### 问题 5：为什么 top-k 不是总是注入多个 skill？

回答：
多注入 skill 可以提高覆盖面，但会增加 prompt token，也可能让模型收到冲突工作流。比如“修复 pytest 失败”可能同时命中 debugging 和 test-writing，但如果第一名明显高于第二名，就没有必要注入两个。

因此我加了分差策略：默认 top-k 是 2，但只有候选分数接近时才注入多个。第一名明显领先时只注入第一名。这是在召回率和 prompt 简洁性之间的折中。

### 问题 6：中文任务是怎么支持的？

回答：
项目的 demo 和开发过程里经常出现中文任务，例如“修复测试失败”“审查 diff”。如果只做英文 token 匹配，路由会不稳定。

所以我加了两层支持：

第一层是 metadata aliases，可以在 skill 里写中文触发词，例如：

```yaml
aliases:
  - 修复
  - 失败
  - 测试
  - 审查
```

第二层是 router 内部的轻量中文 alias 映射，例如“审查”“评审”会直接关联 `code-review`，“测试”“单测”会关联 `test-writing` 或 `debugging`。这样不依赖外部分词库，也能覆盖常见中文任务表达。

### 问题 7：如何调试 Skill 路由？

回答：
我加了 CLI 命令：

```powershell
minicode skills route "审查 diff"
```

它会输出候选 skill、分数、是否被选中以及匹配原因。这个命令有两个作用：开发时可以调权重和 aliases，面试或 demo 时也可以展示系统不是黑盒选择 skill，而是有可解释路由过程。

### 问题 8：Skill 内容是怎么注入模型 prompt 的？

回答：
Agent Loop 在 SELECT_SKILL 阶段得到 selected skills 后，会通过 `SkillRegistry` 加载对应 `SKILL.md`，然后 prompt builder 把 active skills 注入到模型 planning prompt。

为了避免 prompt 过长，我没有无限制注入完整 skill 内容，而是保留必要字段：

- name
- description
- tags
- applies_to
- aliases
- 截断后的 content

这为后续 Day 12 Context Compression 留出了空间。现在先保证模型能拿到足够的工作流指令，同时避免 skill 数量增加后 prompt 失控。

### 问题 9：Skill 路由和 Agent Core 的边界是什么？

回答：
SkillRouter 只负责根据任务文本选 skill，不执行任务、不调用工具、不修改状态机流程。AgentLoop 负责调用 router、加载 active skills、记录 trace，并把 skill 内容交给 prompt builder。

这个边界很重要：Skill 是任务策略，Tool 是执行能力，Agent Loop 是状态机和控制流。三者分开后，后续扩展 Memory、Subagent、Harness 时不会互相缠在一起。

### 问题 10：当前 Skill System 还有哪些限制？

回答：
当前版本是 v1，主要限制有：

- 路由还是关键词和 alias 驱动，不能理解很复杂的隐含意图。
- skill 内容只是截断注入，还没有摘要压缩。
- 还没有外部 skill 安装和版本管理。
- LLM rerank 依赖辅助模型，没有模型时会回退确定性排序。
- 当前只有 debugging、test-writing、code-review 三个内置 skill。

这些限制是有意控制范围。当前阶段重点是把可加载、可路由、可解释、可测试的基础能力跑通，后续再根据 benchmark 结果决定是否加更多 skill、外部 skill 包和更强的 skill 内容压缩策略。
