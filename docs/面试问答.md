# MiniCode Agent 面试问答

这份文档围绕 MiniCode Agent V1 的整体项目设计、工程取舍和可扩展性进行问答，不按开发天数展开。回答重点放在：为什么这么设计、如何保证安全、如何评测效果、后续如何迭代。

## 1. 项目定位

### 问题：MiniCode Agent 是什么？

MiniCode Agent 是一个本地 Coding Agent Runtime。它不是单纯的聊天机器人，而是一个能在 workspace 内观察项目、选择 skill、调用工具、记录 trace、使用 memory、压缩上下文、调用 subagent，并通过 harness 做评测的完整 agent baseline。

V1 的目标是做到 feature-complete：可以本地运行、可以接 OpenAI-compatible 模型、可以扩展 skill、可以评测和做消融实验。

### 问题：它和普通 LLM 代码助手有什么区别？

普通代码助手更偏向一次性问答或补全。MiniCode Agent 更强调运行时系统：

- 工具调用有统一协议。
- 文件和命令操作有权限控制。
- 每次运行都有 trace。
- skill、memory、compression、subagent 都进入同一个 agent loop。
- harness 可以衡量不同功能组合是否真的提升能力。

也就是说，它关注的不只是“模型会不会写代码”，还关注“模型如何安全、可追踪、可评估地操作开发环境”。

## 2. 整体架构

### 问题：项目的核心模块有哪些？

核心模块包括：

- `AgentLoop`：主状态机，负责 load context、select skill、plan、act、observe、verify。
- `tools`：统一工具系统，包括读文件、搜索、写文件、shell、测试、subagent。
- `permissions`：权限和路径沙箱。
- `trace`：记录运行过程、工具调用、权限判断和评测事件。
- `skills`：metadata 驱动的 skill 加载、路由和 LLM rerank。
- `memory`：本地记忆、LLM reflection、确定性 admission rules。
- `context`：长上下文压缩。
- `subagents`：受控的 explorer/reviewer 子 agent。
- `harness`：benchmark 和 ablation evaluation。
- `models`：OpenAI-compatible 模型适配层和 prompt/parser。
- `cli`：`run`、`chat`、`tools`、`skills`、`memory`、`trace`、`eval` 命令。

### 问题：为什么没有一开始就接一个大模型直接执行？

因为 Coding Agent 的难点不只是推理，而是工程边界。模型需要通过工具观察和修改项目，如果没有统一工具协议、权限控制、trace 和评测系统，就很容易变成不可控的 prompt demo。

MiniCode 先把 runtime 做扎实，再接模型。这样即使模型输出错误，系统也能通过 parser、权限层、tool executor、max steps、failed attempt limit 等机制限制风险。

## 3. Tool Runtime

### 问题：为什么所有工具都要走统一 ToolRuntime？

统一工具协议让 CLI、AgentLoop、Subagent、Harness 都能复用同一套能力。每个工具都用 `ToolSpec` 描述输入、风险等级和权限策略，并返回结构化 `ToolObservation`。

这样上层不需要猜测字符串输出，而是可以稳定读取：

- `ok`
- `output`
- `error`
- `metadata`
- `truncated`

这对 trace、retry、compression 和 eval 都很重要。

### 问题：为什么写文件和 shell 命令默认需要 approval？

因为它们会改变用户环境。MiniCode 把风险分成 allow、ask、deny：

- 只读工具通常 allow。
- 写文件、shell、测试命令通常 ask。
- 路径逃逸、危险命令、敏感操作直接 deny。

这让 agent 可以自动完成低风险观察，但不会默认拥有任意修改和执行权限。

## 4. 安全设计

### 问题：路径沙箱如何防止访问 workspace 外文件？

`PathSandbox` 会把工具参数中的路径 resolve 成绝对路径，然后判断是否仍在 workspace 内。如果路径通过 `../` 或绝对路径逃逸到 workspace 外，权限层会 deny，工具不会执行。

这个检查发生在 `ToolExecutor` 层，而不是分散在每个工具里，所以新增工具也必须经过统一安全入口。

### 问题：shell 命令如何控制风险？

MiniCode 使用命令安全分类器拦截高风险模式，例如递归删除、格式化磁盘、关机、`git push`、可疑管道执行和 `.env` 外传等。

即使用户传了 approved，只要命中 deny 规则也不会执行。这样可以防止 approval 被误用成万能通行证。

### 问题：trace 会不会泄露密钥？

trace payload 会做基础脱敏。字段名包含 `secret`、`token`、`password`、`key` 等敏感词时会被 redacted。命令和参数也会经过 safe payload 处理，避免把明显敏感信息原样写入 trace。

V1 的脱敏是基础规则，后续还可以继续增强敏感路径和内容扫描。

## 5. Model Planning

### 问题：模型在系统里负责什么？

模型主要负责 plan 和 decision。它不能直接修改文件或执行命令，只能返回结构化 action 请求。AgentLoop 解析后，再通过工具系统执行。

这样模型负责“想做什么”，runtime 负责“能不能做、怎么做、如何记录”。

### 问题：为什么使用 OpenAI-compatible adapter？

OpenAI-compatible 接口生态广，很多服务都兼容 `/chat/completions`。V1 用最小适配层支持：

- `MINICODE_MODEL`
- `MINICODE_MODEL_API_KEY`
- `MINICODE_MODEL_BASE_URL`

这能先保证模型接入简单稳定，后续再扩展多 provider 或多模型配置。

### 问题：现在需要几个模型？

V1 推荐一个模型即可。当前主 agent、LLM rerank、LLM memory reflection 可以共用同一个 model client。

后续 V1.5 可以拆成两个模型：

- 主模型：规划、代码理解、复杂推理。
- 辅助模型：skill rerank、memory summary、压缩和分类。

Subagent V1 也不需要单独模型，先复用主模型或 runtime 能力，等角色复杂后再拆。

## 6. Skill System

### 问题：Skill 在 agent 中起什么作用？

Skill 是任务策略包。它不是工具，也不是直接执行逻辑，而是告诉模型面对某类任务时应该遵循什么工作流。

例如：

- debugging skill 强调先复现、定位、最小修复、验证。
- code-review skill 强调按风险排序、引用文件行、关注回归。
- test-writing skill 强调覆盖关键路径和失败用例。

Skill 让 agent 的行为更稳定，也让能力可以模块化扩展。

### 问题：Skill 如何路由？

V1 先用确定性 metadata 路由：根据 name、aliases、tags、applies_to、examples、description 与任务文本匹配并打分。

如果启用 `--llm-rerank`，会把 top candidates 交给模型重新排序。即使 LLM rerank 失败，也会 fallback 到确定性结果。

### 问题：外接 skill 怎么实现？

MiniCode 会加载三个来源：

1. 内置 skill。
2. `MINICODE_SKILL_PATHS` 指向的外部 skill。
3. 当前 workspace 的 `.minicode/skills`。

后加载的同名 skill 会覆盖前面的，所以 workspace 可以覆盖团队或内置默认行为。

每个 skill 至少包含：

```text
metadata.yaml
SKILL.md
```

## 7. Memory System

### 问题：Memory System 在 agent 中的作用是什么？

Memory 让 agent 能跨运行保留有价值的信息，例如项目约定、用户偏好、常见失败原因和流程经验。

没有 memory 时，每次运行都像第一次接触项目；有 memory 后，agent 可以更快复用历史知识，例如“这个项目测试命令是 python -m pytest tests”。

### 问题：为什么先做确定性 memory，再做 LLM 自动总结？

因为 memory 是长期状态，错误写入会污染后续运行。V1 先用确定性 admission rules 控制质量，包括 confidence、source run id、重复检测、secret rejection 等。

LLM reflection 只负责提出更干净的候选总结，最终是否写入仍然交给确定性规则判断。这样可以利用 LLM 的总结能力，同时避免把长期状态完全交给模型。

### 问题：如何避免记忆污染？

V1 的防护包括：

- 低置信度不写入。
- 重复记忆不重复写。
- 疑似密钥不写入。
- 每条 memory 有 kind、source、confidence、metadata。
- CLI 支持 `memory delete` 修正错误记录。

后续可以继续加 stale 标记、冲突检测和召回解释。

## 8. Context Compression

### 问题：为什么需要上下文压缩？

Agent loop 会不断产生工具输出。如果所有观察都原样塞回模型，很快会超过上下文窗口，也会增加成本。

MiniCode 的 compression 不是普通摘要，而是把长 observation 和历史状态压缩进结构化 `TaskState`，保留：

- 当前目标。
- 已修改文件。
- 失败尝试。
- 关键观察。
- 下一步建议。

### 问题：压缩什么时候触发？

V1 支持三类触发：

- 单个工具输出过长。
- 最近 observation 累积过长。
- 总历史上下文增长过大。

触发后会记录 `context_compressed` trace event，并统计 compression metrics。

## 9. Subagent

### 问题：Subagent 为什么设计成受控工具，而不是完全自治 agent？

因为 V1 更重视可控性。Subagent 作为 `spawn_subagent` 工具运行，受同一套 workspace、permission、trace 和 tool registry 约束。

主 agent 保留最终决策权，subagent 只负责 bounded task，例如 explorer 看项目结构、reviewer 看 diff 风险。

### 问题：Subagent 有哪些限制？

V1 的 subagent 默认只读，且有 max-step limit。Explorer 只能读文件、搜索、看 git status；Reviewer 主要看 diff、读相关文件并输出风险和测试建议。

这样可以避免子 agent 自己修改项目或无限递归调用。

## 10. Trace 和可观测性

### 问题：Trace Store 解决什么问题？

Trace 回答三个问题：

- Agent 做了什么？
- 为什么这么做？
- 在哪里失败？

它记录 run_started、phase_changed、skill selection、tool request、permission checked、tool finished、context compressed、memory written、subagent events、eval finished 等事件。

### 问题：Trace 对评测有什么作用？

Harness 可以从 trace 中统计工具调用次数、运行时间、失败原因、compression events、subagent calls、memory metrics 等。这样评测不只是看 pass/fail，还能比较不同配置的行为差异。

## 11. Harness 和消融实验

### 问题：为什么要做 Harness？

没有 Harness，很难证明一个 agent 功能真的有用。Harness 把 benchmark task、isolated workspace、success command、metrics 和 report 串起来，让每次改动都能被量化。

### 问题：消融实验如何判断功能价值？

V1 有多组 ablation config：

- `baseline`
- `skill_only`
- `memory_skill`
- `memory_llm`
- `full`
- `full_llm_memory`

通过对比 pass rate、runtime、tool calls、retries、compression events、subagent calls、memory quality metrics，可以判断 skill、memory、compression、subagent 是否带来收益。

### 问题：为什么 eval task 要复制到隔离 workspace？

为了避免任务之间互相污染。每个 eval run 都会把示例 repo 复制到 `.minicode/eval_workspaces/` 下独立运行，这样一个任务的修改不会影响另一个任务。

## 12. CLI 和用户体验

### 问题：为什么要做 `minicode chat`？

`minicode run` 适合单次任务和评测，`minicode chat` 适合真实使用。用户可以连续输入任务、查看最近交互、清空会话或退出。

V1 的 CLI 布局参考 Claude Code 风格：上方状态卡片展示 agent 信息，下方独立输入区域承载交互。

### 问题：为什么还保留 deterministic `--no-model` 模式？

它适合 demo、测试和无 API key 环境。即使没有模型，用户也能演示工具系统、trace、skills、memory、eval 等基础能力。

这也让测试更稳定，不依赖外部网络或模型输出。

## 13. 工程质量

### 问题：如何保证项目不是只能演示一次的 demo？

V1 有几个工程化保障：

- 模块边界清楚。
- 工具、模型、skill、memory 都有接口层。
- 权限和 trace 是统一入口。
- CLI 和 core 逻辑分离。
- 有单元测试、CLI 测试、harness 测试、mock model 测试。
- eval 能跑 benchmark 和 ablation。

当前全量测试已经覆盖主要路径。

V1.2 进一步把 demo 变成可审计报告：eval report 不只展示 pass rate，还按任务列出 prompt injection finding、permission deny reason、team role evidence、worktree patch proposal、memory recall refs 和 context compression refs。面试时可以直接打开 Markdown report，说明每个能力不是口头描述，而是由 trace、benchmark 和测试共同证明。

### 问题：如果模型输出格式错了怎么办？

模型输出会经过 structured parser。格式错误不会直接执行，而是记录失败并进入 retry 或 failed path。工具失败也会被 observation 注入后续模型轮次，直到达到 failed attempt limit 或 max steps。

## 14. 项目亮点

### 问题：这个项目最值得讲的亮点是什么？

可以重点讲五个：

1. 统一 Tool Runtime 和权限网关。
2. Trace 驱动的可观测 agent loop。
3. Skill + LLM rerank 的可扩展任务策略系统。
4. Memory + deterministic admission 的长期状态管理。
5. Harness + ablation 的量化评测闭环。

这五个点说明项目不是简单接 API，而是在构建一个可控、可扩展、可评估的本地 coding agent runtime。

### 问题：相比 Claude Code、OpenHands、SWE-agent，你参考了什么？

MiniCode 参考了它们的思想，但实现上保持轻量：

- Claude Code：本地 CLI 交互、工具使用、项目上下文。
- SWE-agent：把代码任务视为 agent loop + tools + evaluation。
- OpenHands：工程化 agent runtime 和工具边界。
- Hermes-style agent systems：skill、memory、subagent、harness 组合式能力。

MiniCode 的重点是用较小代码量实现一个完整 V1，而不是复制大型框架。

## 15. 局限性和后续迭代

### 问题：V1 还有哪些不足？

主要不足包括：

- 内置 skill 数量还少。
- 工具系统还缺 formatter、linter、apply_patch、浏览器验证等能力。
- memory 还需要更强的冲突检测和召回解释。
- CLI 还没有 streaming tool panel。
- benchmark 任务还偏小，需要更多真实复杂任务。
- 多模型调度还没有完全拆开。

### 问题：V1.1 会优先做什么？

V1.1 应该优先做：

1. 增强内置 skills。
2. 增加 apply_patch、formatter、linter、inspect_repo 等工具。
3. 改善 CLI 的 phase 和 tool call 可视化。
4. 增强 memory 可解释性和冲突处理。
5. 扩展 benchmark 任务。

这些方向能直接提升 agent 的真实使用体验和评测表现。

### 问题：如果继续做到 V2，方向是什么？

V2 可以考虑：

- 多模型配置和模型路由。
- subagent 专属模型和更丰富角色。
- 外接 tool/plugin 系统。
- 项目级 `.minicode/config.toml`。
- 更强 benchmark 和 regression dashboard。
- 更完整的权限审批和变更回滚。

V1 解决“能跑、可扩展、可评测”，V2 解决“更强、更稳、更像长期可用产品”。
